贾维斯 · 多节点主备与故障接替方案

更新：2026-10-07。根据你的最新安排，112作为首选部署主节点，101作为随时接替的备用节点，正在准备的i3作为第三后备。联想64GB继续开发和书房验证。

这是部署目标和实施规则；目前三台服务器已通过SSH连接与硬件读取检查，平台仍运行在联想。主备同步、统一服务入口和故障切换尚未部署。

1. 节点分工

101的第一职责改为接替中心。预发布与恢复演练使用联想或116的独立环境，避免实验代码或数据损坏101的接替准备。

中心接替顺序：112 → 101 → i3。一旦101接管，它就是当前主节点；112恢复后先作为备用，人工选择窗口再切回，避免反复切换。

房间浏览器、语音终端和开发执行节点仍可分布在多台机器；它们共享当前中心的数据与权限，不各自建立另一套家庭记忆。

2. 同时只有一个调度中心

同一时间只有一台中心接受业务写入、调用Pi、派发开发任务和协调提醒。备用节点保持运行环境与数据准备，但不启动当前完整后台。

原因来自现有代码：业务库和执行库使用本机SQLite WAL，启动后会启用后台处理。把完整后台同时在两台机器运行，不能自动形成一致的主备；各自持有的数据、租约和队列会产生不同状态。SQLite WAL要求使用同一数据库的进程处于同一主机，不支持跨机器共享网络文件系统上的活动数据库。SQLite WAL官方说明

每台保存自己的本地数据目录。101的独立恢复库用于验证，不作为第二个在线写库；不使用NFS、SMB共享活动SQLite文件。

3. 101如何做到随时接替

“已安装备用服务”和“具备接替资格”分别显示。101只有同时满足以下条件，才能标记为可接替：

条件检查内容
正式版本一致API、前端、锁定依赖、Pi SDK和数据库结构版本一致
接替数据完整业务库、执行库、Pi会话、知识原件、运行器配置和语音密钥属于同一已校验恢复批次
数据够新显示最后成功批次的时间和同步延迟；失败时保留旧批次并明确降级
本机依赖可用Linux版Python环境、OCR/ASR/TTS、固定程序、目录与必要模型可实际运行
恢复已验证两个数据库完整性、文件哈希、语音密钥和引用原件通过检查；隔离演练不连接真实执行节点
入口已准备统一域名、HTTPS、Host允许名单、房间和节点访问地址已测试
旧主已隔离已确认112停止业务或被有效隔离；仅有HTTP超时不算证明

设计目标是在101已就绪、旧主已确认隔离后，数分钟内恢复中心。实际时间须通过演练测量，不能现在承诺零停机。

接替页面必须显示可恢复到的最后数据时间。同步频率、最长允许滞后、失败提示和降级方式，需要在复制机制实现与实测后固定；不把“随时接替”默认解释成允许丢失几分钟家庭记忆。

待实施的复制流程：生成一致恢复批次 → 传到101暂存目录 → 核对两库、文件、密钥和清单 → 原子标记该批次就绪。半传输批次不覆盖101最后成功的一份，至少保留前一代用于回退。

数据库采用SQLite支持的一致快照方法。官方列出了Backup API、VACUUM INTO及sqlite3_rsync等适用于活动数据库的方式；普通文件复制不能替代它们。SQLite备份说明、活动事务备份风险

具体在线同步实现还需要覆盖跨两个数据库和可变Pi文件的一致性。单独把两库各复制一次，不等于同一业务恢复点。必要时协调短暂写入屏障，并验证知识原件、Pi会话和队列边界；不能只复制一个.db或定时强关整个平台。

现有scripts/backup.mjs要求后端停止，已用于本机升级前完整备份；它尚不是持续主备复制器。现有隔离恢复演练也不能冒充故障接替演练。正式双节点部署前，持续同步与接替保护属于必做内容。

复制和备份同时保留：101的接替材料用于恢复服务，独立历史备份用于找回误删、损坏或错误版本的数据。112的磁盘历史Reported_Uncorrect为6361，与目前清单基线相同；后续仍按原巡检要求对比，数据不只保存在112。

本机PID、守护控制令牌、临时锁和未完成的进程状态不直接照搬。每台中心使用自己的服务管理身份和进程状态；业务身份与原语音密钥按恢复批次保存，节点自身的私钥与机器绑定保持独立。

5. 固定服务入口

所有房间、管理浏览器和执行节点使用一个家庭域名和HTTPS入口，正常指向112，接替后指向101，避免每个房间分别改IP或重新配对。

域名及浮动服务地址在部署时选定并核对；112、101继续保留各自管理IP。原IP目前是DHCP，应先做路由器地址保留。不能现在随意占用一个未确认空闲的IP。

统一入口本身也需要能够接替，不把唯一代理固定在112或另一台单独机器上。推荐中心主备共同承载受控服务地址，切换后网络入口跟随当前中心。地址移动只负责流量方向，不能作为旧主已经停止写入的证明。

HTTPS证书、合法Host和访问源使用统一服务名。现有浏览器登录或房间凭据如果仍有效且已同步，可以继续使用；未同步或已失效的凭据需要重新验证，不自动认定说话人的身份。

断线中的回答、录音和播放会中断，客户端显示恢复状态并重连。不能承诺一次正在进行的语音对话完全无感迁移。

6. 接替与回切规则

第一版按“检测异常 → 告警 → 管理者确认受控接替”实现，不以两台机器互相探测作为自动抢主依据。

  1. 区分API进程故障、磁盘或主机故障、网络隔离；单个进程优先由本机守护恢复。
  2. 接替前确认112已停止或隔离。无法确认时显示“旧主状态不明”，不启动第二个完整调度中心。
  3. 校验101的正式版本、最后完整恢复批次和数据时间；展示数据缺口。
  4. 新中心先进入恢复状态，暂停旧队列自动派发；核对真实节点上的在途开发进程、外部操作、提醒投递和未回报费用。
  5. 核验后启动101、切换统一入口，确认成员身份、Pi、知识、语音和队列状态，再按需恢复监督。
  6. 112重新上线时不自动成为主节点、不反向覆盖101新数据。先接收新主完整批次，再等待窗口回切。

已对外发出的开发命令、部署动作和语音播放，不能仅凭旧快照状态判断未执行。故障恢复不承诺跨节点恰好一次；不自动重跑状态不明的收费任务或外部操作，不把中断显示为完成。

计划切换时可以先停止新请求、处理在途工作、完成最后批次，再转移入口。突发故障只能从已完成的批次恢复，必须如实报告可能未同步的内容。

i3完成接入后，可增加第三方健康见证和备份存放；若要全自动接替，还须实现旧主隔离、主资格与数据同步判定并完成网络分区演练。第三台加入不自动保证安全切换。i3承担第三后备时，再按实测资源优先恢复对话、成员、记忆和提醒，暂缓重OCR、研究及高并发开发。

若采用三节点多数派管理主资格，112和101同时不可达时，单独存活的i3并没有多数派，不能自动抢主；这种情况走确认旧节点隔离后的人工灾难接管。有效隔离需阻止旧主继续执行副作用，仅切换域名或移走服务IP不够。

联想当前的Windows SAPI声音不能直接作为Ubuntu TTS；两台中心需要实际Linux可用引擎或固定高算力语音接口，并分别完成识别、合成与房间播放测试。

部署前核对Node内置SQLite的实际版本。此次本机读取为Node v24.15.0、SQLite 3.51.3；服务器还没有在SSH执行环境检测到Node/npm。SQLite官方已在3.51.3及指定回补版本修复WAL-reset问题，正式部署应核对修复状态及既有回归，而不是只凭Node大版本判断。SQLite WAL修复说明

8. 管理页面需要表达什么

在现有运维和大屏中呈现：当前主节点、112/101/i3角色、版本、待机就绪状态、最后数据批次、同步延迟、数据库/密钥检查、旧主隔离证明、故障原因和切换历史。i3未接入显示“待准备”，不显示在线。

操作入口包括接替检查、计划切换、故障接替、恢复同步和回切。点击切换前显示受影响的房间、在途任务、最新可恢复时间和必要确认，不能只有“在线/离线”绿灯。

这些是后续需要接入的真实功能，不是现有UI已经具备的主备能力。原来“32GB预发布”和“48GB唯一正式主机”的文档保留为历史记录，当前中心分工以本方案为准。
