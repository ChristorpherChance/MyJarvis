## 3 建立真实 Git 基线再对齐最新源码

### 3.1 已保存的no.git状态意味着什么

发布 ZIP 不含 `.git`。来源清单中的提交号是出处，不等于提交对象已在本目录中。09:32 UTC保存检查中112开发根`.git`不存在；没有新的来源核对前不能直接`git pull`，也不能用`git init`后声称恢复了上游历史。

Git 依赖的打包器会实际读取提交对象、树、索引和工作文件字节；仅有一个写在文本中的 SHA 无法满足这些条件。不要伪造上游提交，也不要将整个迁移原件、私有运行数据和依赖目录 `git add .`。

### 3.2 建议的首次对齐顺序

1. 只读保存现有开发目录的来源、四项 Linux 适配文件、现行 `AGENTS.md`/`CLAUDE.md` 和正式建设文档指纹。开发数据位于 home 下的独立目录，保持原样。保存清单不能包含密钥正文或原始聊天。
2. 在新的相邻目录取得已有公开源码分支或已核验完整 Git bundle。保留原作者和提交历史，不把 ZIP 直接覆盖现有开发目录。
3. 核对实际对象存在、提交祖先关系、工作树状态和明确的来源提交。需要使用 Git 网络时，按现有仓库授权执行；本指南本身没有执行网络命令。
4. 在新仓库中建立本次任务独立分支或 worktree。将迁移的 Linux 开发适配作为明确补丁合入：`package.json`、`.gitignore`、`apps/web/vite.config.ts`、`scripts/dev-112.mjs`。逐项比较，不能整体覆盖最新包清单。
5. 保留 Root 正式建设档案、账本和本次保留策略记录。候选分支中的 CC 建设记录有自己的历史，不能覆盖 Root 正式账本。文档合并详见第 14 节。
6. 在隔离副本安装 Linux 依赖、检查开发配置、验证受影响功能。核对无生产数据、正式端口或生产队列被继承，再决定哪个目录作为后续日常开发入口。
7. 原开发目录和 `.migration-original/local` 继续保留；不要为了让 Git “干净”删除历史原件、未知状态或私有恢复材料。

## 5 数据和配置必须隔离

### 5.1 数据不只有一个数据库

API 基础数据是数据根下的 `jarvis.db`，V1 业务记录、命令回执和事件也使用这套基础库。Pi 在数据根的 `pi/` 下保存认证和会话。执行运行器另有 `execution/`；项目监管、工作台 kickoff、计划、决定、自治和监督事项也有各自目录或数据库。知识原件/处理文件、语音密钥和运行资源亦在数据树内。

因此，复制一个活动 `.db` 不等于完整备份；只恢复基础库也可能留下不同步的任务、意图、会话、费用或递送状态。生产发布采用现行完整树快照与隔离恢复工具；`scripts/backup.mjs` 是较早的停止后备份入口，不能未经核对就当成覆盖现行所有新增数据域的完整生产方案。

### 5.2 开发环境变量

当前 112 开发启动器以白名单构造子环境，固定 loopback 地址、开发端口和真实 passwd home 数据目录。已有公开迁移报告确认它排除继承的模型密钥、生产 `JARVIS_*`、TLS、生产队列和 `NODE_OPTIONS` 等。不要通过改成 `env: process.env` 恢复一整个生产环境。

| 变量 | 含义与接手方式 |
| --- | --- |
| `JARVIS_DATA_DIR` | 独立数据根；112 开发入口应固定到用户开发数据，不指向 `/var/lib/jarvis/data`。 |
| `JARVIS_HOST`、`JARVIS_PORT` | 监听地址和端口；开发为 127.0.0.1/43140，源代码独立安装默认 127.0.0.1/3140，不要在 112 混用默认值。 |
| `JARVIS_DEV_API_TARGET` | Linux 开发 Vite 适配使用的 API 代理目标；与实际开发 API 一致。 |
| `JARVIS_ALLOW_LAN`、`JARVIS_ALLOWED_HOSTS` | 如确有 LAN 部署用途，须显式启用并列出精确主机；不允许通配地址或把地址、端口、路径、凭据混为一个 Host。日常开发优先 SSH 转发。 |
| `JARVIS_TLS_KEY`、`JARVIS_TLS_CERT` | 必须成对配置的本机文件路径；证书私钥不写入文档或仓库。 |
| `JARVIS_NODE_CONFIG` | 正式节点角色/数据根/版本配置路径；开发不要继承正式值。 |
| `JARVIS_PYTHON`、`JARVIS_WHISPER_MODEL` | 可选本地 OCR/语音运行器和已经下载的模型位置；Linux 需独立验证。 |
| `JARVIS_PACKAGE_PYTHON` | 打包器使用的 Python；Linux 可明确选 `python3`，不是运行模型的配置。 |

程序读取系统环境，不会自动加载 `.env`。`.env.example` 仅供理解字段，不应填写真实密钥后提交。模型通常通过平台管理页面保存；终端 Claude Code 的通道由原生客户端/CC Switch 管理，与开发平台数据库中的模型配置分开。

### 5.3 凭据怎样取得而不泄漏

- 平台模型：在自己初始化的开发平台中配置必要的开发模型账户；生产配置不自动复制。
- 终端 Claude：使用运行账号已配置的通道，必要时用 `ccswitch` 查看或切换；不把私有设置转成 CLI argv、代码常量或报告正文。
- 生产节点角色、TLS、observer 身份：由现有维护者按受保护配置和服务定义定位，只查看工作所需元数据。正式节点配置常用 `/etc/jarvis/node.json`，TLS 位于相应受保护目录；本指南不提供其内容。
- 101 Agent：保留现有配对身份、私钥和递送账本，不重新配对来绕历史，也不上传本地 journal.sqlite。
- Git/SSH：使用账号自己的既有授权；迁移项目树不代表已经取得外部账号凭据。

排错公开输出限定为字段名、版本、布尔状态、数量、错误分类、路径和指纹。不要打印整份环境、配置、原始 prompt、provider text、原始聊天、Cookie、录音或 base64 原件。


## 7 一条平台改动应该怎样走完

1. **读目标和当前事实。** 用用户目标、客观标准、已保存报告及当前真实代码确定一个有边界的任务。先定位入口和所有调用者。
2. **建立独立工作副本。** 来源提交、未提交修改、费用策略、技术超时/轮次/重试、验证方式写清。用户要求费用只记录，不设金额消费上限。
3. **实现最窄改动。** 不扩大到其它产品或未授权配置；必要契约变更同时处理服务端、DTO、实际页面和旧数据。
4. **验证真实入口。** 适当的定向反例、类型检查、构建，保存原失败及后续修复。已通过组不为凑记录反复运行。
5. **形成可审交付。** APP 提交、后续 ops/report 提交、准确包与清单、日志和已知/未知费用分开。
6. **独立审查和受控发布。** 源码/包核对不能自己替代上线；上线不能自己替代用户现场验收。
7. **同源留档。** 通过原建设工具追加记录，保留决定版本、原证据指纹、失败、未完成项和经验前提。

如果正在做前端问题，必须验证实际用户事件路径：真实组件、实际 Button 默认类型、表单 submit、handler、路由参数及真实数据形状。SSR 或直接调用 handler 有其价值，但不能冒充真实 DOM click、浏览器会话或网络验收。

## 8 项目工作台和 101 固定 CC 监管

### 8.1 两个项目对象与一个平台

“贾维斯平台建设”项目可以监管平台本身的开发和发布工具；“软件工厂”项目监管另一个业务产品。它们在同一 112 平台中，各有项目、目标、任务、原生会话和费用历史。不能把 101 当成另一套正式 Jarvis 中心，也不能把一个项目的成功回执贴到另一个项目上。

**本版R52来自遗留在101上的贾维斯平台返修会话，目标是监管审阅容量；不是软件工厂产品任务。** 7276候选已回收并发布。后继当前run `3c694…`保存为succeeded，主管S67/goal11 waiting_user且enabled=false，没有另发pause/stop或继续命令。接手仍需核后来是否有新活动、对清费用与交付范围后明确移交；不重启旧run/intent，不在101与112并行改同需求。

用户未来的常规平台开发在112。遗留101平台返修完成后，可把已核候选在112独立副本审阅合并；继续保留101作为外部执行节点/工厂工作区，并不意味着所有平台改动以后仍必须经过101。平台任务与工厂任务的项目、task、工作区、native lineage、run/resultH和用量始终分开。

用户在 112 终端直接用 Claude 开发平台，是一条新的日常开发入口，不会自动成为平台已登记的 Agent。若需要由平台正式派发到某个节点，仍须使用已登记的执行器与工作区合同。已有 101 正式链应保留固定原生会话和历史；不要为了绕超窗、未知用量或旧意图失败新建任务洗账。

### 8.2 正式运行链

```text
用户在项目工作台发文字目标
  → 版本保护的 kickoff 或 supervisor command
  → 任务与 session 绑定、持续 goal policy、持久 dispatch intent
  → 101 Agent 签名领取、原生 CC 在固定工作区执行
  → 节点本地 journal 可靠保存日志、结果和用量
  → 中央核对签名结果与报告原件
  → 生成绑定 run/resultH/goal revision 的一次模型判断意图
  → Pi 严格判断 continue / wait_user / review / stop
  → 继续时才形成新有界 run；等待或停止时不冒执行
```

工作台 `GET /api/v1/projects/:id/workbench` 是只读 context；`POST …/workbench/kickoff` 才建立/恢复明确的启动流程。主管命令、adopt、reconcile、纠错都有实际副作用语义，不能当成“查看状态”调用。

`reply` 是执行指令；查询状态应用 GET。运行中输入的文字未必已经送到当前 CC stdin，应按界面和实际合同说明是下一轮指令、草稿还是待本人回答。`reconcile` 也可能在消费有效新结果后触发判断及后继，不能说成纯只读。

### 8.3 修改这些地方时必须保留的门

- `commandId` 相同正文重放返回原回执，异正文拒绝；版本冲突刷新和对账，不盲重 POST。
- pending kickoff 有持久归属，普通调度不能在跨库空隙捡走孤儿任务；paused/blocked 或有旧 run/session 的任务不能悄悄新建或自动恢复。
- claim 仍核对项目、任务、机器、工作区、原生会话、目标修订、授权 generation、source run/resultH 和有界 window。
- 目标的一次持续授权不等于无限工具权限；每轮仍有技术窗口、超时、重试、停止与撤权门。10M 是当前技术软窗口，不是金额上限，也不能冒称 CLI 硬 token cap。
- 未知历史用量不能写 0；已经发生的用量即使超过原窗口仍需真实入账，不能拒收后当作没发生。
- 已 complete/failed/uncertain 的模型意图保原历史；不重放同一次提供方调用。新业务应有合法的新 goal/run/source binding。
- 停止需要对应节点的真实收尾证明；页面显示停止请求、CLI exit0、无输出或网络断开都不单独证明进程组已空。
- Agent 私有 journal 的 ACK、重送、检查点与本机身份必须保留；不要删除 journal 解决“卡住”。

## 9 主管报告和自动判断合同

### 9.1 CC 最终反馈

当前严格反馈对象有七个字段：`state`、`summary`、`question`、`options`、`recommendedOption`、`evidence`、`nextSuggestion`。按实际 schema 填写；`question` 使用字符串，没有问题时写空串。已知非 `needs_decision` 状态的精确 `question:null` 有中央兼容处理，但不要把它当成可以忽略其它类型错误的通行证。

最终总结应先写用户能理解的结果、问题和下一步，再提供小份事实报告。优先独立 UTF-8 JSON/TXT 事实文件，约 1.5–4KiB；完整日志、diff、ZIP 另存，事实文件只索引其真实相对路径、字节数和 SHA-256。不能把只列 H 的索引冒充模型已经读到了那些原件。

当前原件采集硬门为最多 30 件、单件 32768 字节、合计 262144 字节；还要满足安全相对路径、普通文件、无链接、非空、UTF-8、精确哈希等条件。这个限制与 Pi 完整输入限制独立。大 ZIP、整树清单和大 diff 不应直接塞进 `evidence`。

`SUPERVISOR_EVIDENCE_SIZE_INVALID` 等采集错误可能覆盖多种分支；未取到具体安全诊断前，不猜某个文件“肯定超限”。合适的用户文案是“报告回传未通过采集检查”，随后用实际原件定位原因。

### 9.2 Pi 判断

共享受信合同在 `runtime/project-supervisor-contract.ts`。Pi 必须返回六个精确键：

```text
action, directive, reason, selectedOption, criteria, experienceReferences
```

`review` 要逐字使用输入的每条 criterion，唯一、完整覆盖、全部 `met:true`，并引用已验证的精确 path/SHA 对。缺证、改写标准、未知或未满足时只能依据真实情况 continue、wait_user 或 stop；不能把自述成功升级成产品验收。

`experienceReferences` 必须按实际输入逐项回应；输入为空时明确 `[]`。不得把 exclusions、原件正文里提到的 ID 或已失效版本当作可采用经验。未验证不能 adopted；前提、版本、snapshotHash、counterexample、superseded/deprecated 和采用原因都要保留。

### 9.3 完整输入的计量与容量门

当前R52的完整受信合同与投影JSON使用同一131072B（128KiB）UTF-8上限。运行器、适配器和真实PiService.run沿同一常量/完整text口径；旧R51r1的64KiB门及Factory goal9超限原件保留。其它purpose的32000字符门、32K Token上下文与4096输出声明保持；字节不是Token。生产发布健康不等于provider接受任意128KiB输入。

被排除经验只投影 ID、版本、H 和固定原因等元数据，完整冻结审计仍在私有意图中。目标、标准、更正、选中经验、已核原件、绑定和反例所需语义不能为过门被默默截断。必需内容仍超过上限时明确阻断，不把 truncated 参考当作完整权威。

原R51的helper测试绕过真实PiService，旧入口仍按32000字符拒绝，故独审拒发布；R51r1另补真实PiService+SDK离线driver入口组。R52又保存一组生产projection→adapter→真实PiService.run→SDK离线driver的受控组：1/1、4driver、0fetch，构造81717B/25合成原件/49排除与131072B多字节边界可达，超限0新增driver，partial/otherpurpose仍拒异常。它不是实际Factory原prompt回放或真实provider接受；原64KiB组未重跑，源码/包通过不能证明128KiB真实提供方容量。

## 10 测试怎样选才能有用

| 改动 | 最少应核对的入口 | 不能替代的验收 |
| --- | --- | --- |
| API/DTO | 实际路由、validator、SQLite 与版本/重放反例 | 只测内部 helper 不能证明 HTTP 合同可用。 |
| Pi 输入/终态 | 真实 PiService 入口加受控 SDK driver；合法与超限/partial 反例 | fake adapter、离线 driver 不是真实 provider。 |
| 工作台按钮 | 实际 Button 和 form/handler/params；已知和未知数据 | SSR、pattern 匹配不是真实 DOM 点击。 |
| 项目路由 | 初始 URL、旧 task focus、返回/刷新和未知任务 fallback | 不能把未知任务送到别的项目。 |
| 节点协议 | 当前 DTO、claim、签名结果、ACK/journal、停止和迟到结果 | 单 child/helper 不等于 HTTP→runner→真实 CC 全链。 |
| 发布/恢复 | 全 payload/manifest、完整数据快照、隔离恢复、服务账号权限和独立 health | 包存在、安装成功或一次 is-active 不等于业务可用。 |
| 语音/OCR | 受控样本、实际引擎和最终现场终端分层 | 健康接口不证明声音、收音和识别效果。 |

根脚本 `npm run typecheck` 检查工作区；`npm run build` 构建 Web 和 API。`npm test` 运行 API 测试组。按当前任务需要选择具体受影响测试，不为本指南重跑历史全部测试、模型或部署。

例如Pi入口改动可先读本版`apps/api/test/pi-supervisor-entry-r52.test.ts`及其保存TAP（历史入口修复另见R51r1组），再决定本次变更是否需要同组复验。需要执行单个 API 测试时使用仓库实际依赖入口，例如：


## 11 打包与旧浏览器资源兼容

`scripts/package-capture-release.mjs` 只生成本地候选包，不构建、不联网、不安装、不启服务。它核对选定提交对象、索引/跟踪路径、原始 Git blob、当前字节、API sourcemap、编译身份/时序，以及 Web 离线资源有限闭包。

实际参数形态：

```bash
JARVIS_PACKAGE_PYTHON=python3 node scripts/package-capture-release.mjs \
  --version=<新版本> \
  --source-commit=<真实应用提交全SHA> \
  --api-dist=<本次API编译目录> \
  --web-dist=<本次Web编译目录> \
  --output=<全新候选输出目录>
```

先完成并保存本次必要验证，再打包；不为了“报告还没结束”重跑已过 build。APP 提交应先于打包；报告和 release-specific sidecar 的后提交可以另列 FINAL/ops，不能拿后者冒应用包中原始 sourceCommit。

基本交付三件为版本 ZIP、相邻 `release-manifest.json` 和 ZIP `.sha256`。包不含 node_modules、生产配置、证书、模型、运行数据或 `.git`，Linux 依赖另核。构建关联检查不是可复现构建证明，文件类型许可也不是文本隐私审查。

旧网页会继续请求它缓存的哈希 chunk。曾出现旧资源缺失时服务器把 SPA 的 index.html 以 200 返回给 JS URL，造成页面异常；不能仅用 HTTP200 判断资源正常。新包需要保留已核验的旧 immutable asset 闭包，逐文件 H/size 核对，并纳入新 manifest，不能伪称旧 manifest 已包括新增补件。

当前受控包核已逐代保留旧资源；下一版仍须以实际前版包和清单为基准。`promote-web.mjs` 保留工作副本 `dist` 的旧文件，不自动解决全新目录或跨机器发布时的旧资源缺失。
