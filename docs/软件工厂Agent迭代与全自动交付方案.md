用户明确新增两项最终目标：**各阶段 Agent 及子 Agent 持续迭代优化；流程逐项走通后，从客户原始需求开始，全自动产出完整产品文档和可交付、可使用的软件。** 原有端到端质量目标继续有效。

本文将新目标纳入规划。当前人工点和已有产品边界作为实现事实保留，不以它们否定全自动最终目标，也不通过删除质量检查来实现自动化。本轮深入阅读公开设计及源码，更新标准与路线；没有开启全局监督、修改 101 产品代码、调用项目模型或执行新部署测试。

## 1. 最终要形成两条闭环

| 闭环 | 自动完成什么 | 达成依据 |
| --- | --- | --- |
| 项目交付 | 原始资料→范围与需求→设计/全部原型→任务与代码→独立测试→统一修复复验→文档及软件→目标环境使用验证→后续维护 | 每条必需需求有当前真实产物、追溯和测试；交付对象可以实际安装、访问和使用 |
| Agent 优化 | 收集阶段失败/低效→定位能力或流程问题→改 Agent/子 Agent 候选→独立评估→按配置提升稳定版本→观察/回滚 | 候选相对固定基准有可复核改善，必需质量不退化；每次任务可定位实际使用的 Agent 版本 |

第一条负责“把这个项目做对”，第二条负责“以后更稳定地做对”。修好了某个项目不等于 Agent 已优化；修改提示词也不等于后续项目质量改善。

全自动目标允许使用既定标准自动过关。正常完整输入和已配置目标环境下，不要求每个阶段有人点击；运行中仅把无法按既有范围、质量或预算规则解决的具体问题交给管理者或客户。

| 文档与交付 | 需求/设计已有 md/html/docx/pdf 导出；交付导出主要是报告/决定/引用 JSON，备份主要是表与对象键清单 | 同版全部文档/页面/软件/证据实际字节组成完整包，下载校验、独立安装及目标用户使用 |
| 能力优化 | 有人工改善指南、提示词版本及模板基础；所审路径未找到自动评估/比较/提升/回滚闭环 | 版本化 Agent 候选、独立任务集和真实项目反馈，量化改善并保持全链无退化 |

## 3. Agent、子 Agent 和运行实例分别管理

| 对象 | 推荐含义与必需记录 |
| --- | --- |
| 项目总控 Agent | 持有原始目标、需求/候选版本、全流程依赖、交付使用出口及共享资源；组织阶段，处理可解决阻塞并保持质量门 |
| Agent 定义 | 职责、适用阶段、输入/输出契约、模型路由、提示词/工具/技能、验收、预算/停止/恢复策略；定义版本不可变 |
| 子 Agent 定义 | 在父 Agent 的明确子目标内完成专项工作；有自己的版本、输入输出和限制，不自行扩大项目范围 |
| 运行实例 | 某项目、某候选、某轮实际执行；记录父运行、任务、Agent 定义版本、实际模型、工具调用、产物、用量、退出原因 |
| 独立验证器 | 按固定条款和用例检查成果，保留拒绝与复验；不能让产出方自己制造全部预期和通过证据 |
| 阶段负责人 | 拆子任务、处理依赖、汇总相互一致的结果；一个子 Agent 完成不等于阶段全部通过 |

同一 Pi 会话切换角色提示可以作为早期实现，但不自动等于独立子 Agent。真正委派需要可观察的父子关系、执行与产物身份、失败传播、取消传播及汇总检查。无需为了 Agent 数量拆分简单工作；只在独立专业职责、并发或复核有收益时拆分。

推荐层级为：项目总控 → 阶段负责人 → 按需专业子 Agent；独立验证和能力改进横跨各层。委派深度、并发及总轮次明确受限，不能无限递归创建子 Agent。

推荐按业务阶段设置负责人及专项子 Agent：

| 阶段负责人 | 可按需要委派的子 Agent | 阶段成果与复核重点 |
| --- | --- | --- |
| 资料与需求 | 格式/扫描解析、术语与来源整理、业务分析、需求拆解、歧义检查、RTM 核对 | 原文/CRD/PRD/条款及来源；未定事项显式列出，不能臆造客户确认 |
| 架构与详细设计 | 架构、数据、接口、权限/状态、非功能/部署、跨文档一致性评审 | HLD/各册 LLD 与全部需求一致；接口字段、错误、状态和数据契约可实现 |
| UI 与交互 | 信息架构、页面/组件、高保真逐页、整体交互、响应式、设计一致性检查 | 所有独立页面/子页面/状态及整体原型；入口与真实旅程完整 |
| 开发 | 任务规划、前端、后端、数据库、集成、构建、代码审查 | 真实仓库代码、测试/CI/合并；同一候选，无冲突覆盖与模拟完成 |
| 测试与修复 | 测试规划、用例、真实执行、UI 对照、性能/权限、缺陷归类、独立复验 | 全部必测真实执行；缺陷能定位、修复和回归，不让改断言掩盖错误 |
| 发布与交付使用 | 完整打包、文档、安装/迁移、配置、目标环境部署、使用验证、维护 | 文档和软件同版；实际文件及安装入口可用；目标用户角色完成约定旅程 |
| Agent 能力改进 | 失败归因、提示词/工具/技能候选、评估集维护、离线评估、发布观察 | 改善哪种错误、影响什么能力、比较依据及稳定/候选版本明确 |

“资料”和“需求”、“概要”和“详细”等可以有独立负责人或子 Agent；此表是职责推荐，不能冒充当前源码已有相同角色。模型可承担语义分析，构建、数据读取、测试及发布结果由真实工具取得。

## 4. 每个 Agent 都有可执行契约

| 契约项 | 要求 |
| --- | --- |
| 输入 | 项目/条款/产物及内容版本、前置阶段依据、授权范围、可用工具与知识来源；不只是一段模糊聊天 |
| 输出 | 产物类型/位置/版本、承接条款、完成项/缺项、差异/疑点、所需下一步及真实工具证据 |
| 上下文 | 只取当前任务必需资料；精确引用完整文件位置，摘要压缩保留来源；跨项目资料和记忆范围隔离 |
| 工具 | 已有 Pi 接口和真实产品命令优先复用；缺失业务适配器单独实现，不把模型文本当执行回执 |
| 验证 | 结构/版本检查、独立语义审阅、真实运行；不同阶段分别配置，不只统一用模型打分 |
| 子任务 | 父/子 ID、依赖、写入范围、输出集合、汇总规则、错误/取消及预算传播 |
| 限制 | 阶段及项目共享费用/Token/轮次/时间额度；子 Agent 不重复领取整项目额度 |
| 恢复 | 检查点、会话和输入版本、已发生工具副作用、账单/产物对账；不能因超时盲目重做发布 |
| 追踪 | 定义/提示词/工具/技能/路由及真实模型版本、实例、尝试、来源和证据；用户可下钻 |

版本必须实际生效：启动前解析有效提示词/叠加内容/技能/工具/路由/模板及相关文件，形成版本与内容哈希快照；执行器核对收到的内容，运行回执记录实际采用的快照。快照与请求不一致则不能宣称用该 Agent 版本执行。模板套件、项目绑定和默认代码模板只记名称不够，客户模板优先规则、解析后的实际正文及导出器版本均要固定。

Agent 路由按阶段/职责/动作配置。架构、复杂分析、关键质量评阅使用用户指定的强路线 `gpt-6.1-sol[1m]` 作为目标配置；简单整理等可按已验证策略采用快速路线。该模型标识是用户指定路线，不代表本轮验证了有效 Provider、价格或上下文容量。请求模型、返回模型、会话显示及用量归属须一致；切换后备保留原因、输入及新的运行身份。

用量既按项目总账汇总，也能定位阶段、Agent/子 Agent、任务、尝试、工具及 Provider/模型；父级汇总引用子调用，不能把同一调用重复加总。额度在父子间分配和回收，未知费用单列，语义评阅/失败/优化实验的消耗也计入相应预算。

产物变化后，要找到依赖它的子任务和评估结果，重新检查受影响部分。任务并发在独立副本上执行；受控合并后形成新候选与必要回归。模型供应商返回的别名不证明内部版本完全固定，别名和已知模型身份分别记录。

共同候选必须冻结客户原始资料、CRD/PRD、HLD、各册适用 LLD、目录、所有单页/子页/状态及整体原型、开发计划、源码提交、测试配置和报告、发布包之间的依赖。每项记录版本、内容哈希、适用性及承接条款；不适用需要明确依据，不为凑册数生成空文档。分别改变详细设计、某个页面或测试配置时，要定位受影响路径，使旧产物与通过证据过期；无依赖支路可以保留，但不能静默沿用只核三份工件的旧指纹。

## 5. 项目修复与 Agent 优化分开进行

发现问题后先分类：客户输入不足、需求/设计矛盾、上下文缺失、提示词缺陷、工具/接口缺陷、执行环境、模型能力、编排/恢复或验证器问题。不能所有失败都靠“换更强模型”或“再生成一次”解决。

| 步骤 | 推荐机制 | 出口 |
| --- | --- | --- |
| 发现 | 项目真实缺陷、阶段退回、人工修改、用量异常和运行日志产生改进候选 | 有症状、输入、实际结果、版本及影响范围 |
| 归因 | 区分业务错误与 Agent/工具/编排错误；独立核对根因和替代解释 | 有可复现问题或明确未确定原因 |
| 创建候选 | 修改职责、提示词、上下文、工具、技能、模型路由或子任务安排；记录改动假设 | 版本差异明确，候选与当前稳定版隔离 |
| 离线评估 | 同条件比较稳定版与候选，覆盖成功/失败/边界、历史回归及保留的未见项目 | 质量门槛通过，改善可核对，不以平均值隐藏关键退化 |
| 小范围使用 | 在匹配适用范围的后续项目或独立环境观察，绑定候选版本 | 真实质量、费用、耗时和恢复结果符合配置 |
| 提升/回滚 | 达到预先配置的门槛自动提升；退化回稳定版并保留失败 | 新任务使用新版本；在途任务不偷偷换版本 |
| 沉淀 | 有效经验形成版本化技能/评估样例与适用条件 | 经验经验证发布，不能把一次猜测记为通用规则 |

优化优先级：**真实与正确 → 完整和一致 → 稳定恢复 → 成本与速度**。质量相同才比较耗时和费用；未知费用保持未知。人工修订的参考答案也记录依据，不能无审阅地当标准真值。

Agent 可自动提出并试验改进，不代表可以擅自降低验收、删除失败用例、扩大权限或提高预算。自动提升规则属于项目/能力管理配置；规则变化形成新的版本和影响记录。评估数据与验收规则由独立流程维护，生成方不能同时改题、改答案并宣布自己更好。

## 6. 如何衡量 Agent 是否变好

| 维度 | 按阶段真实计算 |
| --- | --- |
| 正确与完整 | 原始要求遗漏、错误解读、设计矛盾、页面/状态缺失、代码与原型偏差、真实用例失败 |
| 首轮质量 | 第一次独立评估达标比例、返工原因及轮数；样本和分母明确 |
| 可追溯 | 输出有来源、版本及承接理由；错项目/错版本/陈旧引用次数 |
| 可信执行 | 模拟冒充真实、假文件/假链接、未跑通过和虚假交付；此类关键缺口不能靠总体评分抵消 |
| 协作与恢复 | 父子汇总一致、取消传播、重复副作用、超时/崩溃安全续做、错误定位与阻塞解决 |
| 效率 | 从同输入到合格成果的总时长、真实用量/费用、工具调用和返工成本，不只单次生成速度 |
| 客户可用性 | 安装/升级成功、约定角色与旅程可用、文档可照做、交付后同类问题复发 |

每次比较固定输入、候选代码、验收标准、工具和已知环境；模型/资源差异单列。小样本或单项目改善只声明该范围，不等于全能力提升。指标阈值按阶段及业务风险设定，尚未测得的指标不预填绿色。

评估集分为开发调试集、固定回归集、保留未见验收集和真实项目观察；客户私有资料在授权范围保管，公开建设记录只引用脱敏元数据。评估集也有版本，基准变化不能与旧分数直接比较。

## 7. 全自动执行的入口与流程

客户入口是提交原始资料或原始需求，不要求客户先写专业 PRD、设计、开发计划或完整验收清单。平台已有或一次配置的通用档案提供默认技术约束、资源额度、质量标准、目标环境和发布/恢复规则；工厂自动从原始输入提炼项目目标、范围、用户/场景、可测试验收条款及缺项，核对来源后形成版本化项目配置。

语言、时区、单位、数字格式、公司文档/品牌模板及目标终端作为共同配置贯穿需求、页面、数据、测试和交付说明；可从原始输入与预设合理确定的内容自动登记。重要歧义才提出具体问题，不伪造客户答复；目标环境或外部凭据使用受控配置引用。预算/权限是运行配置，不能让客户必须先理解 Agent 技术才能提出需求。

原始输入完整性需要独立出口：登记文件/页/章节/表格/图片/附件及语言、原文定位和处理状态；长文分段、检索与覆盖对账，不能只送开头后声称全覆盖。扫描、损坏/加密文件、格式限制、截断和相互矛盾各自记录；OCR 疑点保留原图定位并校对。资料和引用作为数据，不能改变执行权限、预算或验收规则。未能证实完整性的必需输入不能静默正式通过。

正常流程：

**接收/核对资料 → 形成需求并检查 → 设计与全部原型并核对 → 分解任务 → 真实开发与合并 → 独立测试 → 缺陷修复/复验 → 完整包和产品文档 → 目标环境部署/安装 → 使用核验 → 交付归档及维护。**

| 运行机制 | 要求 |
| --- | --- |
| 就绪调度 | 输入、前置结果和资源有效才运行；阶段通过后自动创建/安排后续工作，不靠人逐条补任务 |
| 自动质量门 | 原有定稿/批准/转换/交付点由可核对的规则、语义评阅和真实证据决定；保留决定记录 |
| 自动返工 | 检查发现问题，生成具体修复任务；在既有边界内修复、复验、更新依赖，不只提示“请人工处理” |
| 持久状态 | 阶段/父子任务/输入版本/候选/证据及决定持久保存；服务重启不丢进展 |
| 一致性 | 严格区分执行结束、验证通过、可发布、已部署和可使用；并发、晚到回执不能错放行 |
| 停滞识别 | 没有新证据或实质变化时定位原因，调整已授权策略或明确阻塞；不能无限发“继续” |
| 副作用 | 同一构建/迁移/发布用稳定操作身份；失败先核对是否已发生，再决定续做或回滚 |
| 管理者介入 | 随时查看、暂停、取消、改目标；改变影响下一候选及相关证据，取消不能自动复活 |

客户追加需求或改变验收属于新输入版本，自动形成影响分析和下一迭代安排。软件工厂的源码完善、工厂内部客户项目流水线及 Agent 优化分别有预算和候选，不互相污染。

## 8. 现有人工点怎样过渡为自动质量门

七个人工点是当前设计/配置事实。用户现在明确全自动最终目标，路线需包含替代人工逐关操作的能力。先逐项取得真实通过/拒绝证据，再将适用项目配置为自动模式；不是永远保留所有人工点击，也不是本轮直接改成自动通过。

| 当前确认点 | 全自动模式应核对的依据 |
| --- | --- |
| 需求定稿 | 客户来源和必需范围完整、重要歧义已解、条款可测试、RTM 及语义一致 |
| 设计/原型共同定稿 | HLD/LLD/全部页面与交互齐全且一致，版本匹配，无必需断链 |
| 开发计划批准 | 需求承接、依赖、工具、执行空间、预算及验收就绪 |
| 开发转测试 | 真实当前构建、自测、代码审查和合并有效，候选及输入固定 |
| 测试计划批准 | 全部必需条款及适用页面/状态有用例，独立环境及分母明确 |
| 验收报告定稿 | 必测实际通过，修复复验、遗留及证据对应当前候选，不接受模拟/零用例/错版本 |
| 交付决定 | 同一已验候选、完整文档/软件、安装升级恢复、目标环境实际使用和已配置发布策略符合要求 |

这些质量门的规则、责任和决定身份需可查询，自动拒绝要说明条款和证据。语义门可用独立 AI 辅助审阅，实测与文件真实性必须由工具支持。客户满意或合同签收若需要客户本人表达，应如实记录；不把机器验收伪称客户已经签收，也不自动为每个项目追加商业签字作为阻塞。

自动化还要覆盖七关之外的写入动作：资料/内容定稿、设计各册定稿、需求/设计补丁接受、计划建议处置、缺陷复验关单、构建/版本交接等。当前一些源码直接要求 `human`，测试计划还会强制 `AT-MANUAL` 必测；后续要按模式和真实验证能力改造，不能冒用人工身份、直接写通过或仅调整七关 mode。可自动的浏览器/业务用例由真实执行器验收；确实只能由人判断的内容列出具体原因和解决安排，不能称全自动正常路径已走通。

## 9. 异常情况下也能连续推进

| 异常 | 期望的处理与验收 |
| --- | --- |
| 额度/限流 | 按已验证路线及额度策略等待或切换；保留上下文、检查点和真实费用，不让未知金额当免费 |
| 网络/进程/节点中断 | 原进程、回执、用量和工具副作用对账后安全续做；不能只有服务自动重启 |
| 模型或工具结果不合格 | 定位具体错误，有限修复或使用已验证备选；重新独立核验 |
| 父/子部分失败 | 保存已合格子产物，阻止缺项通过；按范围补失败部分，传播暂停和取消 |
| 上游变更/并发写入 | 受影响候选与下游待复验；旧通过历史保留，合并后重新判断当前状态 |
| 外部接口不可用 | 按契约降级/重试/阻塞策略处理，模拟只能明确单列，不能正式通过真实能力 |
| 输入不足或目标冲突 | 若已有规则可确定则继续并记录；无法决定业务含义时提出具体问题，保存工作等待答复 |
| 预算/权限/使用目标不具备 | 列出真实差额或缺失及可选安排，不能默默提高额度、越权或换假目标 |
| 发布/迁移失败 | 停止扩大影响，按确定的恢复策略恢复并核对结果；记录失败，不重复执行未知副作用 |

全自动正常路径和异常安全续做分别验收。管理者主动暂停/取消是有效控制，不应被系统当异常自动“修好”。

## 10. 交付必须走到客户可以使用

| 交付对象 | 最小完整要求 |
| --- | --- |
| 产品文档 | 原始需求/CRD/PRD及决定、HLD/LLD、独立高保真页面和整体原型、开发说明、测试/缺陷/验收、发布与变更说明；按项目适用范围明确 |
| 软件成果 | 源码/锁文件、可运行包或镜像、清单哈希、必要静态资源/迁移、配置示例、接口或集成说明 |
| 安装与使用 | 环境要求、安装/初始化/升级、账号和权限配置方式、实际入口、典型任务、导入导出/附件及常见故障处理 |
| 运维与恢复 | 服务/数据位置、监控与日志入口、备份和回滚、已知限制、受支持版本与依赖恢复 |
| 交付身份 | 项目/客户/候选/需求设计和 Agent 版本、软件包/配置/数据结构及实际运行版本，下载和访问范围 |
| 使用验证 | 在约定目标环境，以约定用户角色完成关键旅程；写入读回、重启持久化及必要文件操作正常，说明与实际一致 |

项目开始形成适用交付目录，并由工厂自动产出：需求/澄清/RTM、设计、原型、开发与接口/数据说明、测试/缺陷/验收证据、安装/配置/迁移/升级/回滚、用户手册及管理员运维/备份恢复、版本说明、已知问题及第三方依赖/授权清单。文档以同构建软件和真实操作核对，不能仅填统一模板标题。

完整包包含实际文档、独立页面及整体原型、源码/可运行软件、必要迁移和可交付证据文件字节，统一清单记录各自身份、版本、哈希、采用的 Agent/模板/配置与依赖关系。报告/决定引用 JSON、数据库逻辑备份、软件交付包分别管理；对不应交给客户的内部聊天、私密配置和原始日志只保留受控脱敏引用。由独立环境实际下载、解包，检查文件齐全、字节与清单一致、没有错误项目或私密内容，再按说明安装和运行。

导出和下载有独立检查：各约定格式的文本、表格、图示、链接、字体/目标语言、分页及可打开性，实际导出字节固定并校验；从最终客户入口检查授权、签名过期/续取及必要大文件/断线场景。存在四格式导出接口不代表这些内容与链路已经通过。

仅形成台账、ZIP 可下载或接口健康，不等于交付可使用。部署目标缺失时，自动完成可复现包和独立安装核验，清楚保留目标环境待配置；不能声称客户环境已运行。最终全自动“交付使用”验收必须使用实际已配置目标，而不是一直停在这个待办状态。

客户包可用性与工厂备份恢复分别验证。恢复需要一致快照、实际文件对象及全部适用关系（包括原型页/模板绑定等）和可恢复依赖；只有对象键清单不能证明离线可恢复。交付使用还包含必要初始化、权限/账号配置、用户/管理员操作引导、监控/备份和问题反馈接管，凭据受控交接，不公开附在包里。

工厂自身的升级部署和客户软件的交付分别管理。原 PRD 客户产品生产自动发布原为分期；本轮全自动最终目标要求相应交付/安装/目标环境适配进入路线，按用户指定环境实现，不推定任何未知客户生产账号或权限已经存在。

## 11. 全自动达标分阶段证明

| 阶段 | 需要取得的证据 | 达标后开放什么 |
| --- | --- | --- |
| A：单阶段真实 | 每个阶段真实输入、产物、独立验收，合格和不合格正反例；前后承接完整 | 可自动执行该阶段及有限返工，保留当前模式清楚可见 |
| B：Agent 可迭代 | 稳定/候选定义版本、独立评估、子任务汇总、提升/回滚及未见项目对照 | 可按已配置策略优化并使用合格能力版本 |
| C：端到端贯通 | 代表性多页面项目从新输入到全套文档、真实代码、测试修复、完整包、实际安装使用 | 明确场景已贯通，不能外推所有业务已支持 |
| D：正常全自动 | 从提交完整原始需求后，无逐关人工点击，全部质量门及使用核验自动完成 | 适用项目可选择全自动模式 |
| E：异常与变更 | 额度/中断/父子失败/陈旧输入/重复回传/迁移失败及需求变更，实际恢复和受影响复验 | 无人值守可按范围连续运行，遇真实缺项有明确处理 |
| F：稳定使用 | 多次独立输入、不同场景和代表性环境，24/72 小时观察及版本维护，质量/用量有记录 | 在已证明的适用范围持续全自动交付 |

验收包含必要的真实失败修复，但不靠在业务环境故意制造破坏来补证据。故障注入在独立环境进行。具体样例、次数及质量/时间/费用阈值依据需求和基线配置，不能在没有结果时预填通过。

| 视图 | 管理者看到什么 |

| 交付与维护 | 同版文档/软件/测试/运行、下载、使用核验、后续缺陷与变更安排 |
