# 贾维斯 · 服务器权限选择与授权

更新：2026-10-07。支持五档权限、手动填写服务器、下载权限脚本与SSH连接清单。账号和服务名有就地填写说明。上方HTML选择器仅生成方案；查看或下载不会改变服务器权限。

## 1. 现在是否拥有全部权限

**当前101、112、116三台的superopen账号均已具备完整免密sudo权限，可通过sudo执行root操作。** 普通SSH登录仍是superopen；需要管理员操作时使用sudo。

这次实际检查同时确认了NOPASSWD: ALL规则和sudo -n /usr/bin/id -u返回0。不是只依据sudo用户组或一次认证缓存推断。实际版本为sudo-rs 0.2.13-0ubuntu1.2，结果见[权限审计](../artifacts/server-permissions-qa/permissions.json)。

| 服务器 | SSH账号 | 当前实际权限 | 本次是否修改权限 |
| --- | --- | --- | --- |
| 101 · 192.168.10.101 | superopen | 完整免密sudo，可取得root | 否 |
| 112 · 192.168.10.112 | superopen | 完整免密sudo，可取得root | 否 |
| 116 · 192.168.10.116 | superopen | 完整免密sudo，可取得root | 否 |

早期清单只记录smartctl与dmidecode的免密授权；当前实际配置已经更高。SSH公钥脚本负责获得账号访问权，完整权限来自服务器已有sudo配置，本次工具没有自动给三台扩权。

完整权限指Linux系统管理员权限，可管理软件、文件、服务、网络和用户。平台中的任务审批、第三方账户授权等仍按各自规则处理。

## 2. 五种可选档案

| 选择 | 参数 | 新增权限 | 适用情况 |
| --- | --- | --- | --- |
| 普通登录 | login | 不新增sudo授权；移除本工具对该账号的旧sudo授权 | 普通开发与文件操作 |
| 硬件巡检 | diagnostics | 固定SMART读取、内存信息读取 | 专用巡检账号 |
| 应用运维 | operator | 巡检，以及指定非root服务的状态、日志、启动、停止和重启 | 贾维斯日常自动化运维 |
| 完整管理·需密码 | admin-password | 全部sudo命令，使用PASSWD规则 | 由人交互管理的独立管理员账号 |
| 完整管理·免密码 | admin-full | 全部sudo命令使用NOPASSWD规则，可取得root | 明确授予完整管理权的管理机或部署工具 |

硬件巡检通过root持有的固定封装执行smartctl -a和dmidecode --type memory，不直接授权smartctl任意参数。应用运维只操作选择的固定服务，日志关闭分页器，不授权任意shell、任意服务或软件安装命令。

普通登录仍能修改该账号有权限的文件，不应称为“全系统只读”。真正的受限账号还取决于目录权限、所属组和其他sudo规则。

## 3. 不同电脑想要不同权限怎么办

**sudo权限属于Linux账号，不属于某一把SSH公钥。** 多台电脑都登录superopen，就都继承superopen的完整权限。想按电脑或用途区分，使用独立账号和独立密钥。

| 建议账号 | 用途 | 建议档案 |
| --- | --- | --- |
| superopen | 当前主管理和首次部署 | 保留现有完整管理权限 |
| jarvis-ops | 日常平台运维 | 应用运维 |
| jarvis-watch | 硬件巡检 | 硬件巡检 |
| jarvis-admin | 另一个管理员 | 按需要选择需密码或免密码 |
| jarvis运行账号 | 后台进程 | 普通账号，由部署流程设置必要目录权限 |

**给已经拥有完整权限的superopen选择巡检档，不会自动剥离其完整权限。** 本工具只修改自己管理的文件，保留其他sudo授权、用户组、现有公钥与SSH配置。要降低现有账号的实际权限，需另外核对并撤销其原授权；这次未执行降权。

sudo、Docker、LXD、disk等组可能带来额外权限。独立账号应用后检查id与sudo -l，不能只凭档案名称认定受限。需密码档还需要设置该账号密码，并检查其他免密规则及sudo认证缓存；工具不读取或设置明文密码。

## 4. 各字段怎么填，其他机器怎么用

服务器下拉框已加入“手动填写其他服务器”。它不要求新机器先进入项目清单，可离线生成独立脚本。IP、主机名和主机指纹都应填新服务器的实际信息，不要照抄示例。

| 字段 | 填写规则 | 示例 |
| --- | --- | --- |
| 服务器编号 | 自定标识，1–64位字母、数字、短横线或下划线；开头是字母或数字；合并清单时须唯一 | i3-backup |
| IP地址或域名 | 服务器实际地址，不加协议、端口或路径；IPv6不加方括号 | 192.168.10.120仅为示例 |
| SSH端口 | 1–65535整数，默认22；修改过SSH端口则用实际值 | 22 |
| 实际主机名 | 在服务器执行hostname，粘贴完整结果；权限脚本应用时检查此值 | jarvis-i3仅为示例 |
| 现有管理账号 | 服务器已有的普通Linux账号；应用权限须由具备sudo的现有管理员执行 | superopen或ubuntu，以实际为准 |
| 授权账号 | 被授予所选权限、以后登录服务器的Linux账号；不是Windows用户名、家庭成员或项目名 | jarvis-ops |
| 管理服务 | 只在应用运维档填写；指定已安装的systemd服务名，包含.service，区分大小写 | jarvis-platform.service |
| ED25519主机指纹 | 从服务器本机或可信渠道读取真实SHA256指纹；只下载权限脚本可留空，下载SSH清单必填 | SHA256:后接43位指纹 |

授权账号支持1–32位小写字母、数字、短横线或下划线，以小写字母或下划线开头，不允许root；完整管理仍通过普通账号加sudo实现。已有账号直接填写其真实名称，新账号可填写jarvis-ops、jarvis-watch或jarvis-admin，并勾选“账号不存在时创建”。创建不会设置密码或授权SSH登录，也不会把普通账号自动加入sudo组。

“沿用现有管理账号”会把该服务器的管理账号填入授权账号；“使用独立账号”会按所选档案提供建议名称。选择需密码管理档时，管理员还要在服务器设置账号密码，例如sudo passwd jarvis-admin。表单不收集密码或私钥。

管理服务不是网址、项目目录、Docker容器名或启动命令。可在服务器执行以下查询；最后一行的服务名换成你的真实服务：

~~~bash
systemctl list-unit-files --type=service
systemctl show jarvis-platform.service --property=User --property=FragmentPath
~~~

服务名与查询方式见[systemd服务说明](https://github.com/systemd/systemd/blob/main/man/systemd.service.xml)、[systemctl官方说明](https://github.com/systemd/systemd/blob/main/man/systemctl.xml)。

服务必须已安装、使用非root账号运行，其定义文件、附加配置及父目录由root持有且不能被普通用户改写。jarvis-platform.service目前只是贾维斯预定服务名，尚未部署到服务器；不能据示例认定它已经存在。不知道服务名、准备首次安装或配置Docker时，先用现有管理员完成部署，其他权限档不需要填服务名。当前工具每个账号管理一个指定服务；给同一账号改选服务会替换本工具原来的服务授权。

### 情况A：新增一台i3或其他Linux服务器

1. 在新服务器本机执行whoami、hostname，以及下面的主机指纹查询。
2. 选择“手动填写”，按实际填写地址、端口、管理账号、主机名和指纹。选权限档与授权账号；未部署服务时暂不使用应用运维档。
3. 下载权限脚本，交给新服务器现有管理员；在目标服务器先预览，再明确应用。若新服务器没有sudo，须由它的现有root管理员完成授权，本工具不能凭空获得管理员权限。
4. 下载连接清单，生成新管理电脑自己的SSH公钥包，给授权账号添加公钥，再验证登录。权限授予和SSH公钥授权分开执行。

~~~bash
whoami
hostname
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256
~~~

下载的权限脚本以主机名防止误用；IP和端口用于标识及后续SSH连接，不会在权限安装时检测网络地址。手动填写的机器显示“尚未核验”，即使编号与已有112相同也不会继承112的审计结论。

### 情况B：另一台电脑访问已有服务器

服务器选择它要访问的101、112或116；授权账号选择它要登录的服务器账号。与联想一样使用superopen，就继承该账号现有完整权限，无需再授予sudo，只需添加新电脑的公钥。需要更低权限时，使用独立账号和独立密钥。

例如公司HP仅管理112的贾维斯服务：服务器选112，授权账号填jarvis-ops，档案选应用运维，服务填部署后的真实服务名。由112管理员应用一次权限和公钥授权，然后在HP生成并保留自己的密钥。

HTML会按当前选择生成SSH连接清单；清单里的user是授权账号，不是另填的现有管理账号。下载后放到项目目录。下面示例中office-hp是管理电脑标识，换成home-pc、lenovo等即可；文件名随选择变化，使用页面显示的命令：

~~~powershell
node scripts/server-access.mjs prepare --inventory servers-112-jarvis-ops.json --output artifacts/server-access/office-hp-jarvis-ops --client-id office-hp --identity-dir ~/.ssh/jarvis-ops
node scripts/server-access.mjs verify --output artifacts/server-access/office-hp-jarvis-ops
~~~

先执行prepare生成授权包，再让服务器管理员按目标账号安装其中的公钥，之后执行verify。新电脑不复制旧电脑私钥或ssh-config；不同角色使用独立的密钥目录。新电脑需要Node.js、OpenSSH及[通用授权工具](通用服务器授权工具.md)所列文件；不需要安装整套贾维斯。HTML选择器本身可独立离线使用。这套服务器授权脚本面向Linux；Windows目标机需要另用Windows账户与OpenSSH权限流程。

SSH公钥记录在目标账号的authorized_keys中，参见[OpenSSH公钥授权说明](https://man.openbsd.org/sshd#AUTHORIZED_KEYS_FILE_FORMAT)。

## 5. 如何授予完整权限或其他档案

在HTML选择器里选服务器、档案、账号和服务，再下载脚本。脚本默认只预览，应用时必须由服务器现有管理员执行。

以112为superopen生成完整免密管理方案：

~~~powershell
node scripts/server-permissions.mjs prepare --inventory config/servers.example.json --output artifacts/server-permissions/admin-full --server 112 --profile admin-full --user superopen
~~~

将生成的permissions-112-superopen-admin-full.sh放到112，用superopen登录后先预览，再明确应用：

~~~bash
bash permissions-112-superopen-admin-full.sh
sudo bash permissions-112-superopen-admin-full.sh --apply
sudo -l
sudo -n /usr/bin/id -u
~~~

当前三台已经有完整权限，通常无需再次应用该档案。以上流程用于新服务器或明确需要新增授权的账号。

为112创建独立运维账号的示例：

~~~powershell
node scripts/server-permissions.mjs prepare --inventory config/servers.example.json --output artifacts/server-permissions/operator --server 112 --profile operator --user jarvis-ops --unit jarvis-platform.service
~~~

~~~bash
bash permissions-112-jarvis-ops-operator.sh
sudo bash permissions-112-jarvis-ops-operator.sh --apply --create-user
~~~

--create-user仅在账号不存在时新建普通账号，不为它加入sudo组；系统权限由所选档案授予。应用运维档要求指定服务已经安装、使用普通用户运行，且服务定义及父目录由root持有、不可被普通用户改写。当前贾维斯服务尚未部署到三台，因此该档应在服务部署后应用。

账号创建与SSH授权分别处理：在该账号下执行[通用公钥授权脚本](通用服务器授权工具.md)。管理员代为操作时，先把新公钥脚本放到该账号可读取的位置，例如/tmp/authorize-112.sh，再以目标身份执行：

~~~bash
sudo -iu jarvis-ops env -u SUDO_USER -u SUDO_UID -u SUDO_GID bash /tmp/authorize-112.sh
~~~

使用独立密钥目录，避免复用已经能登录完整管理员的同一把密钥。例如将新清单config/servers-ops.json的user改为jarvis-ops，其余主机信息与指纹保持真实：

~~~powershell
node scripts/server-access.mjs prepare --inventory config/servers-ops.json --output artifacts/server-access/ops-lenovo --client-id lenovo-ops --identity-dir ~/.ssh/jarvis-ops
~~~

上面的委托命令由管理员明确切换到jarvis-ops，并清除原sudo调用的标识变量；公钥脚本仍检查实际用户名与HOME所有权。不要直接sudo bash公钥脚本，把授权误写到root。权限安装脚本自身则要求root。

## 6. 工具会改哪些文件

| 位置 | 作用 |
| --- | --- |
| /etc/sudoers.d/80-jarvis-access-账号 | 本工具独立管理的sudo规则；权限0440 |
| /usr/local/libexec/jarvis-permissions/账号 | root持有的巡检和运维封装；权限0755 |
| /var/backups/jarvis-permissions/change.随机编号 | 修改前的本工具规则、封装与本次方案；仅root访问 |

安装前检查现有sudo语法、目标账号、所有权、链接和目录写权限；拒绝覆盖无本工具标识的文件。新规则先用visudo校验，最后再检查整套sudo配置，失败恢复本次涉及的管理文件。同一账号的权限修改通过锁串行处理。

普通登录档只撤销本工具管理的sudo规则，不删除账号、公钥、其他sudo文件或其他人的授权。权限安装不会自行重启服务、安装软件或修改SSH登录设置。新建账号若后续安装失败可能保留，但不会因该步骤自动获得完整管理权限。

现有所有完整权限规则不能靠新增低档规则“覆盖成受限”。真正降权需单独审核其他来源；不会假装降权成功。

## 8. 我的推荐

首次部署直接使用当前superopen完整权限，能准备运行环境与开机服务。平台进程用普通服务账号运行；日常自动化另设jarvis-ops，硬件巡检另设jarvis-watch。需要让新管理电脑执行完整部署时，明确给其独立账号选择完整管理档。

权限属于账号及其sudo配置；原理与授权语法可参考[Ubuntu用户管理](https://documentation.ubuntu.com/server/how-to/security/user-management/)、[sudo项目示例](https://github.com/sudo-project/sudo/blob/main/examples/sudoers.in)。当前Ubuntu使用sudo-rs，因此本工具使用实际服务器的visudo验证兼容性，避免依赖不支持的命令参数通配规则。[sudo-rs参数支持说明](https://github.com/trifectatechfoundation/sudo-rs/issues/1455)
