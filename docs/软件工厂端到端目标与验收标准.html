本次用户明确的目标：贾维斯指挥并核验 101 软件工厂最新代码打包部署；各阶段产物完整、合格、相互承接；各阶段 Agent 与子 Agent 可迭代优化；流程走通后，从客户原始需求到最终产品文档及软件交付使用全自动运行。

明确目标纳入目标基线；示范业务、性能数值、费用额度及自动模式的具体质量门配置仍需落实。已有人工点和分期边界记录为当前设计/实现事实，不否定用户新增的全自动最终目标。本轮形成标准和深入公开源码审阅，没有执行新部署、产品测试或修改软件工厂源码；不能把要求当作已实现能力。详细角色、改进、全自动过关及使用标准见 Agent 迭代与全自动交付方案。

1. 目标与验收对象

对象 要证明的结果 检查对象
软件工厂本身 最新明确版本能打包、安装、运行、升级、恢复；各模块实际工作 工厂自己的 PRD、设计、原型、源码、构建和数据库
工厂生产的业务项目 客户资料能够形成正确需求，经过设计、开发和验证，得到可运行交付物 该客户项目自己的需求、设计、页面、代码和证据
贾维斯监管 能组织两层工作、发现遗漏或不一致、安排有限修复、核对结果并管理版本 真实任务、执行器、产物、测试、用量及操作记录

必须分别记录两层验收。工厂自己运行正常，只证明部署或相应功能可用；还需要真实业务示范证明其生产能力。业务项目的 PRD 或页面也不能拿来验收工厂自己的界面。

用户第 1 条要求属于贾维斯对软件工厂本身的外层发布监管。原工厂 PRD 将“自动把客户项目发布到生产”列为扩展范围，两者分别登记，不能混淆或据此删掉第 1 条目标。

目标完成的总体条件：全部必需条款有真实合格成果，产物和证据对应同一有效版本，无阻断缺陷；完整文档和软件包可安装、运行及按约定角色使用；升级、恢复、Agent 改进与自动模式分别有验证。正常完整输入下，无需逐关人工点击，按已配置质量门自动形成交付决定；未执行、模拟、未知和旧版本结果单独展示。

2. 十个阶段与出口标准

阶段之间可以迭代，完整出口不能省略。每次推进使用已固定的输入版本；上游发生变化，先分析影响，再更新相关下游。

阶段 必需产物 达标检查 进入下一阶段的依据
① 原始需求与范围 客户原件、访谈或补充记录、场景/角色清单、疑点与范围清单 解析未漏附件/表格/关键原文；明确目标、边界、冲突、优先级和验收方式 歧义有结论，原始要求逐条登记；新增推导要求单独标来源
② PRD 原子需求条目、业务规则、流程、数据要求、非功能要求、验收条款、追踪矩阵 每条原始要求有承接或明确范围决定；无无依据删改；失败分支、权限与边界清楚 范围及版本确认；本期必需需求全部可检查
③ 概要设计 架构、模块、主要流程、依赖、部署和数据流设计 所有功能与非功能需求有设计承接；跨模块责任及技术约束不冲突 需求—模块/流程关系完整；重大设计取舍有依据
④ 详细设计 接口/错误、数据结构/迁移、状态机、权限、后台任务、交互规则、异常与恢复方案 足够直接实施和测试；接口、页面、数据和状态转换相符；不存在只有标题的空章节 必需条款有可执行细节及测试条件，版本与概要设计匹配
⑤ 高保真原型 页面/子页面/状态清单、可独立查看的高保真页面、完整可交互原型、组件规范 页面齐全，主要和异常旅程可走通；字段、权限、按钮及流程遵从设计；适用视口覆盖 每个 UI 相关条款对应页面与状态；整体交互经过核对
⑥ 开发计划与代码 承接设计的任务、依赖、验收、源码差异、真实单测/CI、独立代码审查、实际合并回执、真实构建及接口/数据实现 任务覆盖全部本期需求；源码真实实现；UI 与批准原型一致；单测/CI 有退出码及报告；不是仅写进度为完成 当前候选的必需任务有代码与验证依据，审查及合并可核对，未完成项显式列出
⑦ 从零独立测试 清洁环境说明、初始化、用例、实际结果、UI 对照、缺陷和原始执行证据 空环境能安装运行；全部本期必需且适用的旅程/边界/权限/异常/恢复用例实际执行通过；必测不能用跳过代替 结果绑定测试对象、构建、输入、用例和环境；工程检查及各包约定覆盖率达标，缺失证据不算通过
⑧ 缺陷修复与复验 统一缺陷台账、修复任务、提交、新构建、同用例复验和影响回归 原错误确实解决，无改断言掩盖问题；受影响功能通过；旧失败保留 阻断缺陷有独立复验，P0/P1 无未关闭项；遗留决定不得豁免本期必需条款
⑨ 打包、发布与验收 可运行包/镜像、文件清单/校验、迁移/备份、部署记录、冒烟与回滚、交付报告 发布的就是已验证候选；前端/接口/数据一致，域名访问及关键业务正常；失败可恢复 已部署版本可识别、运行验证完整，最终交付决定记录清楚
⑩ 运行维护与变更 版本台账、实际使用核验、运行观察、故障、回归策略、需求变更和下一版计划 目标环境以约定角色完成业务；故障可定位，变更可追溯并触发复验；旧发布与决定保留 每次迭代重新形成范围、候选、测试及发布链，用户可实际使用

每个阶段分别显示：输入就绪、产物存在、完整性、内容质量、上下游一致、验证状态。文件存在、生成成功或模型评分高，都不能单独让阶段显示为“验收通过”。

3. 101 最新代码怎样打包部署

“最新”必须指向可核对的内容。在创建候选时同时记录 Git 提交、工作区实际文件指纹、未提交改动、明确纳入的新增文件、依赖锁和工具版本。打包过程中发生变化，需要重新固定候选，不能把同一 HEAD 当成相同代码。

推荐执行顺序：只读检查 → 固定独立候选 → 构建与打包 → 隔离部署 → 运行核验 → 形成发布结论 → 按授权策略更新正式实例。新代码可以在候选环境部署验证，产品未正式验收的事实保持可见。

检查环节 需要确认的内容
发布基线 源码/文档/锁文件版本一致；未提交内容是否纳入明确；正在运行版本与目标候选分开
实际构建 在固定候选上执行类型、编译与必需检查；保留退出码和真实输出，不用生成桩代替
两种包 源码包用于重建；可运行包或镜像用于部署。均有文件清单、版本、校验和用途，不能只登记台账
包内边界 包含必须的资源、迁移、配置示例和说明；凭据、真实业务数据、私人输入和运行日志由受控配置/存储管理
部署目标 固定机器、目录、服务、端口、数据卷和访问入口；候选与现有业务实例隔离
运行核验 进程及依赖就绪；前端不是白屏，静态资源和 API 匹配；授权登录、关键业务操作、写入读回及附件等适用能力实际正常
访问链 若目标提供域名访问，还要检查 HTTPS、代理路由、登录会话、下载与流式连接；本机端口通不能替代域名链验证
数据与恢复 当前数据备份有效；空库初始化和上一版升级分别验证；回滚明确代码与数据兼容性，不能只有换回旧程序
恢复依赖 配置、模板、提示词、执行器、模型路由及系统级套件纳入受控清单；不在项目备份中的依赖另有恢复来源与验证，私密值仍由授权配置保存
发布后 记录实际运行构建、配置版本引用、数据库迁移版本、资源与错误观察；失败停止扩大发布并核对恢复结果

构建通过、服务健康和产品交付是不同结论。健康检查返回 200 不能证明需求全部实现；上线时用的包与测试包哈希不同，也不能复用原验收。

4. PRD、设计和原型怎样检查质量

4.1 原始要求到 PRD

客户一句话可能包含多个条件，需拆成可验证条款，再保留原文定位。原件解析还要检查图片/表格/附件、扫描识别疑点和约束说明。无法确定的内容进入问题清单，记录提出、答复及采用结论。

PRD 至少涵盖：目标和范围、用户/角色、场景/旅程、功能与业务规则、数据、异常与边界、权限、非功能要求、外部依赖、验收、明确分期。必要的工程推导可以补充，但应标为推导来源，不能伪称客户原话。

完整性检查按原始需求和本期批准范围逐条做；语义评审核对意图、条件、否定、单位及边界。关键词相同或链接存在，不能证明意思相同。抽样审阅有范围声明，不能称“所有需求无遗漏”。

4.2 PRD 到概要/详细设计

每个需求都要有设计承接。非 UI 要求可由后台、数据或运维设计承接，不能强行每条配一页，也不能因此没有实现/测试位置。

核对前端字段、接口、数据字段、权限和状态转换的同义关系；补齐幂等、并发、失败恢复、超时、重试及外部依赖。应当能从详细设计直接拆出实施任务和测试，不需要执行器临时猜规则。

4.3 全部独立高保真页面与整体交互

页面清单需含主页面、子页面、详情、编辑、弹窗/抽屉、权限场景及适用状态：正常、加载、空数据、错误、成功、校验失败、未授权、禁用、上游改动导致下游陈旧等。适用性逐项说明，不能只覆盖首页或顺利流程。

两类成果同时验收：每个页面/子页面能单独查看并定位其版本；整体原型能实际完成相关旅程，包括跳转、返回、筛选分页、提交、失败提示及恢复等。原型使用模拟数据可以，但应明确其模拟范围，不能算真实后端或模型已通过。

布局、组件、颜色、字体、间距、字段、文案和交互规则形成共同基线；桌面/手机等按当前项目范围逐页验证。不同页面和视口的错误不能靠全局平均隐藏。

4.4 代码与 UI 一致性

实际程序使用固定测试数据、页面状态和视口，与批准的原型版本逐页对照。分别检查信息结构、视觉关键项、字段/控件、交互、权限及数据行为；截图相似度不能替代点击行为，也不能证明后端约束正确。

动态时间或随机数据的视觉忽略范围需明示，不能遮掉关键控件。经过批准的实现改动同步更新设计/原型和版本关系，不能把所有差异都解释成“优化”。

5. 关联必须包含版本和语义

建立这条可双向查看的关系：

原始资料及条款 ↔ PRD 需求 ↔ 概要/详细设计 ↔ 页面与状态 ↔ 开发任务 ↔ 代码/构建 ↔ 用例/运行 ↔ 缺陷/修复 ↔ 发布。

关系记录 必需信息
身份 工厂或客户项目 ID、条款/产物 ID、类型及所属阶段
版本 当前版本、内容哈希、来源版本、候选构建和测试批次；不只存可覆盖的 URL
精确位置 原文段落、文档章节、页面/状态、接口/代码位置、用例与执行结果
承接理由 为什么这个设计、实现或用例满足该条款，谁核对了内容
状态 待产出、待检查、合格、失败、阻塞、待复验；历史版本的原结论保留
责任与依据 产出者、独立检查者、采用决定、实际报告及费用/任务引用

检查至少找出四类问题：有需求无承接、下游无来源、版本不匹配、链接完整但内容不符合。一个需求可以对应多份设计和多条测试；一个通用组件可以服务多条需求，但必须有明确覆盖范围。

以下只是示意，不能算当前已有实现：客户要求“未审批的申请可以撤回，已经审批不能撤回”。

条款 设计 原型 实现 测试与证据
REQ-012A：未审批可撤回 状态机、撤回接口和数据更新 申请详情的待审批状态及撤回确认 服务端状态校验、实际撤回及读回 待审批撤回成功，同构建真实结果
REQ-012B：已审批不可撤回 审批态禁止转换规则 按规则隐藏或禁用操作，并给解释 接口同样拒绝，不能只靠前端隐藏 直接 API 请求也拒绝；审批/撤回并发按约定处理

若下游提供“所有状态均可撤回”，即使文档、代码和测试都有 REQ-012 链接也不合格。若增加审计、幂等等工程要求，登记推导依据，不修改原始客户陈述。

6. 从零测试、统一修复与复验

“从零”包含两个维度：清洁环境安装测试，以及一个真实客户示范从原始资料走到交付的完整旅程。既有服务冒烟和旧数据上点几次按钮都不够。

测试范围 必须取得的真实依据
清洁安装 从固定源码/包、受控配置和空数据库开始，依赖、迁移、初始化及启动可复现
工厂自身 当前适用单元/集成、接口、模块命令、真实浏览器旅程、权限及持久数据校验
工程门槛 当前约定的类型/构建/依赖等检查，逐包真实单测与 CI、退出码及报告；独立代码审查和实际合并回执可核对，各包覆盖率按实测及既有门槛判断
各阶段生产 真实输入产生文档、原型、代码及构建；人工修改/确认、退回、补齐和重新生成按设计工作
示范交付 一份未参与生成和实现的预设验收清单，核对业务项目实际成果；不能只让生成方自评
异常与恢复 无效输入、重复/并发、断流/超时、额度/权限问题、暂停取消、节点重启、资源不足；按本期需求及适用场景验证
UI 每页、子页、适用状态和视口的行为/视觉对照，全部必需用户旅程真实走通
升级与发布 空库安装与旧版数据升级分别验证，发布后冒烟、备份恢复及回滚范围明确

使用独立数据库、文件存储、服务和测试数据；不清空现有运行数据。模拟 Provider 可用于明确的契约或故障注入测试，真实 AI 生产能力仍需有相应真实运行证据及费用记录。网络和模型价格、预算或依赖不具备时记录具体阻塞，不能悄悄改成模拟成功。

完整测试的分母来自本期已确认的必需条款及全部适用用例，不等于“现有测试目录全跑完”。发布前必测全部实际执行通过，约定工程门槛同时满足；未跑、跳过、未知及批准不适用分别列明，不能用空分母、历史报告或跨包平均制造全绿。

每条缺陷记录：唯一 ID、影响条款和版本、复现条件/步骤、预期与实际、严重性、证据、责任任务、修复提交/构建、原用例复验、影响回归和关闭决定。统一状态建议为：发现 → 确认/归类 → 安排 → 修复待验 → 复验通过/失败 → 关闭或重新打开。

同一根因可合并处理，但保留每个表现和需求影响；误报、环境问题、波动、重复和需求变更分别标记。不能删除失败、改预期迎合错误实现、把所有失败都转成“环境问题”，或只凭开发者说已修好就关闭。

建议严重度基线：P0 为严重数据损害、越权或系统不可用；P1 为关键旅程/必需能力不可用、错误放行或没有可靠替代；P2/P3 为影响较低的功能或体验问题。具体等级按实际影响判定。正式发布不得留下未关闭 P0/P1，也不得留下未实现或未验证的本期必需条款；其他遗留只有在确实不阻断必需验收、影响和解决版本明确、采用决定可追溯时才可接受。变更范围需另留决定，不能用降严重度绕过必需验收。

修复先跑原失败用例，再跑影响范围；阶段结束跑必需完整回归。没有实质变化时按有限次数停止无意义重试，保留诊断和下一步建议。

建议保留小型冒烟示范，再增加一个多页面、含详情/编辑/附件或导出/状态转换的代表性项目，证明子页面、交互和追溯。具体示范业务及范围待确定，旧单页待办示范不能独自证明全部生产能力。

7. 发布后的版本与需求变更

事件 推荐管理规则
新版本 记录需求/设计/原型基线、源码指纹、包哈希、迁移、配置引用、测试报告、发布日期、目标及运行结果
发布失败 留下失败及真实恢复状态；代码、数据库、文件及必要系统级配置/模板依赖按兼容性恢复，不用“重启完成”代替恢复验证
线上缺陷 绑定实际运行版本和影响范围，进入统一缺陷台账；热修复也有新候选、最小必要回归和发布记录
客户需求变更 保存原始请求、理由、优先级；分析影响、费用和兼容性；范围确认后建立新版本，不直接覆盖原 PRD
上游改动 沿关系找到受影响设计、原型、任务、实现、测试和发布候选，标记当前目标待复验；历史旧版证据保留原结论
下游实现偏离 判断缺陷或有理由的设计变更，按采用决定更新相应基线，避免事后补文档替错误开脱
持续运行 观察就绪、错误、资源、关键业务和证据可访问性；根据变更影响及可靠性目标安排回归，不无必要全天重跑收费模型
退役与恢复 保留可用版本、依赖、数据策略和恢复说明，明确证据保留、访问及清理方式

已有目标、预算及发布策略内的常规工作自动推进；当前规则不能决定的范围冲突、额度或目标变化再交管理者处理。七个人工点保留为当前事实，用户已明确成熟后全自动的最终目标，后续需逐项替换为有证据的自动质量门，保留辅助模式和可查询决定；不永久要求每阶段手工点击，也不立即绕过当前门禁。

9. 判定口径与贾维斯管理视图

你要求的“无遗漏”按本期已明确必需条款 100% 有承接、有可检验结果执行目标定义；不等于承诺客户尚未表达的隐含要求也已全部发现。未明确项、推导项和分期项公开展示。

原工厂 PRD 的 RTM L0a≥95%、L0b=100%、L0c=100%，以及逐页/视口 UI 关键项 100%、一般项≥95%、严重偏差 0 是已有口径。它们不自动等于本次更明确的“所有必需条款无遗漏”。后续落实时形成补充验收及口径协调记录，不直接修改 101 的旧阈值或历史签收。UI 的百分比也不能让一个必需页面或业务能力缺失被平均掩盖。

范围、语义一致性和真实性分别检查。结构检查核对条目、引用及版本，独立内容评审核对意图与设计，真实工具验证代码和行为；成熟后按已配置标准自动过关与交付，需人裁决的业务歧义单独处理。证据缺失、必测未跑、错版本或模拟冒充真实，阶段不能正式通过。
