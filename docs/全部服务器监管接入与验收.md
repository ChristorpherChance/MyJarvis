## 3. 监测如何运行

112的独立监测服务连接5台服务器 → 各服务器读取本机资源和固定服务状态 → 各节点用自己的Ed25519密钥签名 → 112核对设备、签名、路径及时间 → 中央Agent接口再次核验 → 保存设备和服务观察。

所有节点均使用独立jarvis-monitor账号，无sudo权限。监测SSH公钥由root固定，只允许运行采样器，客户端指定其他命令仍返回固定采样结果。账号不能读取贾维斯业务数据；没有授予开发、服务重启、发布或任意命令执行能力。管理员原有连接账号与权限继续独立使用。

监测不新增公网监听端口。各节点的签名私钥留在本节点，112的连接私钥留在112。项目内只有公开清单、脚本和验收记录，没有管理员密码、会话或私钥。

## 4. 后续机器如何接入

先使用[通用服务器授权工具](通用服务器授权工具.md)为管理电脑建立专用密钥和固定主机指纹，再填写config/servers.managed.json中的服务器名称、用途和固定服务单元。

接入前检查主机名、指纹、Python/OpenSSL及服务是否真实存在；全部检查通过后才安装轻量采样器并配对。新增记录通过正式后台接口保存，在线状态来自真实签名心跳。工具重用已有设备、服务、配对和密钥，并保留原有监测节点。

~~~powershell
npm run server:onboard -- --check
npm run server:onboard
npm run server:verify
~~~

服务器清单不接受任意命令或服务名称中的命令片段；每台绑定最多32个服务。其他管理电脑需先生成自己的连接包，并调整清单中的公开连接包路径。

当前统一采集节点固定为112。增加新的贾维斯主备中心、调整主节点或建立其他跳板链路，需要配套修改部署和接替配置，不是只填写一个地址即可自动生效。

## 5. 部署和备份

112和101使用相同的20261007-managed-stable正式代码。112平台运行；101平台仍停止，两个节点的主备观察均运行。116和两台云服务器安装轻量监测，不部署完整贾维斯中心。

监测单元为112上的jarvis-cloud-relay.service，已开启自启和失败重启。名称沿用上一版以保留既有配置，现在负责全部5台服务器。节点采样器位于/opt/jarvis-cloud-agent/collector.py，固定配置位于/etc/jarvis-cloud-agent/node.json。

扩展监测前的配置保存在112的/var/lib/jarvis-control/monitoring-backups。版本切换前的配置和业务数据保存在各中心节点的/var/lib/jarvis-control/pre-managed-stable（前一次接入备份仍在pre-managed-servers），上一版发布目录保留，可据此恢复。

101尚未实现持续业务数据复制和自动故障接替。当前监管由112提供，112整体停机时监管也会暂停；不能将本次接入描述成已经具备无损自动接替能力。

页面每15秒直接更新设备和服务记录；默认活动历史省略周期采样，避免每次打开平台加载全部心跳。签名采样原始事件、运行趋势和业务操作历史仍保留；需要核查完整事件时，事件接口默认返回原始历史。

## 7. 验收依据

- 5台主机固定指纹、主机名、实际硬件与服务预检通过。
- 接入执行两次，第二次重用全部配对；仍为5台正式设备、5个监测Agent、28个服务，原有云节点身份保持不变。
- 5台真实签名心跳、资源读数和28个服务状态均由正式后台保存；后续心跳持续刷新。
- 5个监测账号均无sudo、不能读取平台数据；从112请求其他命令，仍只能运行固定采样器。
- 正式页面9项交互检查通过：5台实际资源、主机去重、周期事件加载优化、设备详情、28项服务、冷备与WireGuard状态、后续心跳和手机布局；无页面脚本错误，TLS证书校验开启。
- 112与101编译产物和依赖锁文件摘要一致；112业务和主备观察运行，101只运行主备观察。正式接口确认完整周期采样仍可查询，页面只需加载43条业务事件。
