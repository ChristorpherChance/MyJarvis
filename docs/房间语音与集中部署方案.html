贾维斯 · 房间语音与集中部署方案

本文保留2026-10-05的房间方案。2026-10-07更新：中心改为112主节点、101接替、i3第三后备；房间仍访问当前唯一活动中心，具体同步、统一入口与切换规则见多节点主备与故障接替方案。下文早期“唯一主机”和“32GB预发布”属于历史安排，正式服务器及主备切换尚未部署。

1. 统一部署边界

位置职责
48GB 正式主机提供完整网页、Pi SDK 会话、家庭身份与权限、业务接口、任务调度、知识与记忆记录、房间协调、审计和配置
客厅、书房 i3浏览器显示对话和大屏；轻量语音组件负责本地唤醒、拾音、播放、设备心跳与恢复
厨房／餐厅 i3同上，待客厅、书房通过后验证抽油烟机、餐具声、电视声和实际拾音距离
高算力机器如继续采用此前分工，提供 ASR、TTS、文本推理及批处理接口，由 48GB 主机统一调用
联想 64GB / 桌机 32GB开发测试 / 预发布与恢复演练，不作为家人长期依赖的正式入口

网页资源由 48GB 主机统一发布，各终端浏览器访问同一个平台。房间端不部署完整业务后台，不保留独立长期记忆库。终端的短音频缓冲与必要设备配置属于边缘交互能力。

平台集中在 48GB 主机，与模型计算是否使用其他机器是两件事。原先高算力接口仍可保留；若要求模型计算也全部留在 48GB 主机，需另测这台第七代 CPU 的实时识别、合成及多房间并发，不能仅凭 48GB 内存承诺大型模型体验。

2. 浏览器访问的两种方式

方案使用方式优点边界与推荐
纯浏览器打开房间网页，授权麦克风；按键说话，或运行网页本地唤醒模型零业务客户端安装，网页统一更新，适合电脑、手机临时对话与首轮试用依赖网页、浏览器权限、播放策略及设备不休眠；需要专门验证后台与断线行为
浏览器＋轻量语音组件网页负责图像、字幕和控制；组件独立负责麦克风、唤醒、播放与心跳可随系统启动、进程异常后恢复；有屏幕时保留完整主题，没屏幕也能对话固定房间入口首选；只安装一次小组件，业务仍集中在 48GB 主机

纯浏览器唤醒在技术上可行，不必把所有环境声持续发送到服务器；例如 Porcupine Web SDK 支持网页本地唤醒和自定义词，但有账户、AccessKey 与模型配置要求。是否选用须评估实际中文效果和许可。本项目首选评估开源 sherpa-onnx 自定义关键词检测，其官方文档提供中文及中英模型；最终以所选模型许可及家庭实测决定。

安装成 PWA、全屏运行可以改善入口体验，但不构成常驻收音和自动恢复的保证。Chrome 官方说明包含页面隐藏、冻结与丢弃状态，且正在播放或捕获音频的页面可能受到保护；不能简单断言所有后台页面一定会停止，也不能承诺所有浏览器长期运行都稳定。Chrome 页面生命周期。

3. 推荐的房间交互链路

  1. i3 的本地组件监听已配置唤醒词；环境声只保留短暂内存缓冲，不持续上传、不默认保存录音。
  2. 听到唤醒词后，本地给出提示音；48GB 主机选择响应房间，避免邻近终端同时回答。
  3. 唤醒后的必要音频送至平台语音入口，平台调用 ASR，将文字交给 Pi 做对话和意图分析。
  4. 平台根据已确认的成员和会话读取相应记忆、知识或业务资料。身份不明确时使用家庭公共范围。
  5. 回复调用 TTS，音频回到被选中的房间播放；浏览器同步字幕、主题动画和处理状态。
  6. 支持结束会话、继续追问及打断。回声处理要利用自身播放参考，避免把贾维斯的声音再次识别为用户输入；完整打断效果需在具体麦克风、扬声器和房间中验证。

Pi 复用文本推理、会话和工具接口；音频输入输出、唤醒、回声消除由语音模块完成。平台发出的文字或播放指令不能代替真实播放、执行或停止回执。

4. 房间端的最小功能

功能推荐行为
设备绑定管理员配对，绑定房间及终端身份；终端仅获得所需权限，不保存管理员密码
常驻运行固定终端开机启动语音组件，网络与设备断开后重试；系统休眠期间不能保证唤醒
网页显示开机打开房间专用页面，默认仅对话；空闲时可显示家庭公共大屏
无屏模式屏幕关闭或网页退出后，组件继续负责语音；机器和音频设备仍需在线
音频设备选择固定麦克风与扬声器，优先测试具备回声处理的 USB 会议设备；硬件能力不能仅由接口名称判定
静音与留存清晰可见的静音状态，优先物理静音；默认不长期保存原始音频，文字与记忆按已配置策略处理
故障状态平台离线时明确提示暂不可用，不把未发送任务显示为完成；默认不暗中转云端
更新业务网页统一更新；组件单独版本化，升级失败可回退，设备上报真实运行版本

初期由组件通过加密连接与中央平台传输音频、事件和播放回执，浏览器也只连接中央平台。浏览器不必直接连接本机组件，避免再增加本地跨来源接口。控制可使用 WebSocket；音频先采用受控流式传输，若实测需要再评估 WebRTC，不提前引入完整媒体服务器。

每个终端每次会话只有一个音频采集／播放所有者：纯浏览器模式由网页负责，组件模式由组件负责，网页关闭自身麦克风与自动朗读。音频段、回复、播放和停止回执绑定会话 ID、轮次及序号；断线重连核对当前轮次，不重复上传或补播已经停止、过期的回复。

5. 多房间与家庭成员

房间 ID、终端 ID、成员 ID、会话 ID 分开保存。房间里说话的人不一定是房间的主人。个人唤醒词和声纹只能帮助选择档案，不能直接获得私人记忆或管理员操作权限；私人内容及管理动作需要进一步认证或授权。

客厅、书房可以各自独立对话；多人同时使用时分别绑定上下文。相邻房间听到同一次唤醒，由中央协调器结合校准后的检测分数、音频信噪、时间及房间规则选择一端；不能只凭未经校准的分数判断最近房间。

跨房间接续先支持明确请求，例如“到书房继续讲”。平台转交原会话和播放位置，停止原房间播放；不默认将所有个人内容向全屋广播，也不承诺无需传感器就能准确跟随人员移动。

6. 浏览器访问需要的基础设施

房间浏览器建议使用可信 HTTPS 地址，例如内部域名 https://jarvis.home.arpa；这是示例，尚未配置。需准备局域网名称解析、受终端信任的证书、正式入口与设备／成员权限。单纯访问 http://192.168.x.x 不能作为浏览器收音方案的正常前提；localhost 的开发例外不等于普通局域网 IP。MDN 麦克风与安全来源。

纯浏览器首次需授权麦克风，并处理音频播放启用；浏览器可能限制没有交互的有声音自动播放。MDN 音频自动播放。固定终端使用原生组件播放可减少对此的依赖；不能靠关闭浏览器安全机制充当正式部署。

当前开发版本的服务只监听 127.0.0.1，后端还校验本机 Host 和来源，因此其他终端现在无法直接使用此地址访问。先在书房联想完成本机流程；准备48GB部署时验证HTTPS、受控来源、设备配对和权限，再从书房浏览器访问正式主机。32GB可作为预发布或恢复验证节点，按需启用。局域网访问需要完整网络配置，不能只改监听地址。

7. 实施顺序与验收

  1. 在当前联想64GB继续补齐业务接口，先验证真实记录、Pi对话、显式意图确认与管理员权限；家庭独立登录和房间协议随后接入。
  2. 先在书房用当前联想64GB笔记本验证完整界面、Pi文字／任务理解和浏览器按键语音；配置中央语音引擎后再验收“说话 → 平台识别 → Pi → 合成播放”的真实链路。
  3. 书房联想流程通过后部署到48GB正式主机；书房浏览器作为独立客户端连接，验证备份、版本回退、重启与实际网络访问。
  4. 再接入其他房间i3；加本地唤醒、回声处理、自动启动、心跳、静音、断线恢复和打断。先测试单房间，再验证独立成员会话、多房间并发与唤醒仲裁。
  5. 按现场测试接入客厅、厨房／餐厅，测试电视、抽油烟机等背景声。卧室暂不接入。

验收记录应包含唤醒命中及误触发、识别错误、从说完到首段声音的延迟、播放中打断、连续运行、服务／终端重启恢复和多房间身份隔离。先设目标、现场测量，再决定引擎与资源配置，不提供未经测试的秒数或成功率承诺。

8. 当前实现状态

现有联想开发机提供完整前端、管理员 Pi 文本对话及可选浏览器识别／朗读。当前识别文字先进入草稿，本机服务不接收原始录音；它还不是免触屏家庭语音链路。

48GB 正式部署、中央 ASR/TTS、房间常驻组件、唤醒仲裁、家庭身份及跨房间接续尚未实现。本方案确立后续部署边界和推荐实现路线，不将规划内容标为已完成。
