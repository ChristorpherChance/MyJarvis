人工接管与回切顺序

  1. 先确认故障范围及旧主状态，并实际隔离旧主。网络失联本身不能证明旧主已停用；不能在旧主仍可能服务时启动另一主节点。
  2. 核对待用副本的完整清单、SQLite、语音与凭据配套、发布版本及原 900 秒新鲜度。stale 或信息不明时保留阻断原因，不以完整传输记录替代当前就绪证据。
  3. 按已有受保护角色流程处理节点配置：明确唯一主、节点身份、角色代次、发布版本、数据根及观测授权。新主仍为 standby 时不能启动业务；旧主恢复联网前须先按实际安排降为 standby 或保持隔离，避免两个 primary 同时服务。
  4. 在唯一主条件成立后，由维护者明确启动业务，再核对该节点的实际角色、版本和业务健康。新主若要提供语音，须显式启用并启动 jarvis-voice.service，再核对常驻服务及实际语音结果；冷备的 resident 不会因接管或复制而自动启用。
  5. 回切同样先隔离当前主、核对最新数据及未完成任务和外部调用，再更新角色代次并确认唯一主。重新作为冷备的节点应停止并禁用业务与常驻语音，保留所用快照时点、配置绑定及结果。数据回退需另行确定实际范围，不能自动覆盖切换后新增的数据。

本轮没有新增自动故障接管、自动回切或持续数据复制。只读 readiness、observer 健康、源码审查、依赖安装或一次隔离恢复都不授予自动切换能力。软件工厂十分钟自动跟进继续保持暂停，101 上的软件工厂开发节点与平台冷备分别管理。

3. 本轮新增后台

接口 作用
GET /api/runtime/cluster 当前中心、节点角色、版本、恢复材料与阻断原因
GET /api/runtime/cluster/nodes 已登记节点及新鲜观测
POST /api/runtime/cluster/check 对固定节点做TLS、身份、时间和响应校验
GET /api/runtime/cluster/snapshot 本机核验的完整恢复点
GET /api/runtime/cluster/nodes/{id}/readiness 判断恢复材料是否就绪，始终不授予接管权

以上接口仅管理者本人可访问。检查请求不接受临时URL，不修改角色，也不启动备用业务。后台每15秒检查已登记节点，机器中心同步刷新；过期或失效观测显示未知。Pi增加原生只读工具jarvis_platform_nodes，身份撤销后旧工具不能继续查询。

角色配置为standby时，实际启动入口在打开业务库前拒绝启动。主节点运行中角色、代次、版本或授权目录变化时停止业务。旧生产目录的启动保护避免联想再次使用原家庭数据启动第二个中心。

4. 数据迁移与恢复点

迁移先暂停原业务，生成完整一致备份，再恢复到两台服务器。逐文件SHA256、业务库和执行库完整性均核验通过，原语音密钥保留。迁移中暴露的Windows语音路径、服务账号目录权限和启动入口问题已修复并增加实际进程及恢复测试；不完整尝试均保留，未覆盖原库。

最终恢复批次：migration-20261007043835235；恢复点为2026-10-07 12:38:38（北京时间）。两台核验相同完整清单的11个文件，包括业务库、执行库、Pi及运行资料和语音模型。11表示此时实际文件数，不表示业务功能数。

Windows本地语音程序转换为Linux程序。系统内部拥有的文件路径按数据根转换；开发项目和外部知识目录的Windows路径不假装在Linux存在，后续需要在对应执行节点配置。

两台前后端发布文件共180个，逐文件哈希一致。备份留在联想和两个节点的受保护目录；升级前另有112完整快照。角色、证书和观测凭据与业务库分开管理。

目前没有持续复制器。 101的数据不会自动跟随112变化。恢复点超过15分钟或版本、依赖核验失败时，管理页面会明确取消“恢复材料就绪”。这不影响112正常运行，也不能用修改阈值代替实际同步。

5. 语音和知识处理的实际状态

两台使用固定Node24.15.0、独立Python3.12.15和已记录的依赖版本。Ubuntu自带Python3.14保留，OCR运行在独立环境中。

实际服务账号已执行本地语音合成、Whisper CPU识别及中英扫描OCR；原模型随完整备份迁移，运行时不下载。当前TTS是espeak-ng基础离线声音，自然度有限。Piper程序与适配器已准备，但自然语音模型下载未成功，尚未切换；也可配置真实HTTP语音引擎。

语音识别和合成可运行，不等于真实麦克风、房间回声和免触碰唤醒已验收。专业中文唤醒与声纹仍待接入。Pi真实对话仍需配置实际模型账户或本地模型地址；语音会话、身份、预算和工具链继续使用已有Pi SDK。
