连接并使用 AI 开发

在当前电脑的 PowerShell 或 Windows Terminal 中：

ssh 112

进入 112 后：

cd ~/All-Projects/MyJevis
claude

Claude Code 会读取项目中的 CLAUDE.md，并按其要求遵循 AGENTS.md 和建设记录约定。ccswitch 可切换已配置的 Claude 通道。开发使用普通账号，不使用 sudo claude 或 sudo npm。

启动开发页面

在本机终端建立 SSH 转发并登录：

ssh -L 45173:127.0.0.1:45173 112

在该远程会话中启动：

cd ~/All-Projects/MyJevis
npm run dev

然后在本机浏览器打开 开发页面。需要同时用 Claude 修改代码时，再开一个终端执行前面的 ssh 112 和 claude。

npm run dev 和 npm run dev:112 均进入新的 112 开发入口：API 为 127.0.0.1:43140，前端为 127.0.0.1:45173；前端代理指向该开发 API。端口占用时会拒绝启动，不停止已有进程。按 Ctrl+C 结束时，只收尾本次入口启动的进程组；收尾过程中再次发送停止信号，会强制结束同一个自有进程组。

普通 SSH 会话断开时，开发入口收到 SIGHUP 会关闭本次开发服务。需要断线后保留会话时，先用 tmux new -As jarvis-dev 进入 tmux，再运行开发命令；tmux 保留远程会话，重新连接后可接续。浏览开发页面时仍需要本机的 SSH 端口转发连接。

只检查安全配置和端口、不启动应用或写数据库：

npm run dev -- --check

需要验证改动时，在项目目录运行：

npm run typecheck
npm run build

开发数据与保留文件

开发数据固定使用 passwd 账号真实主目录下的独立目录：

~/.local/share/jarvis-dev-112

新开发环境不继承生产家庭数据、平台内的模型配置或生产运维队列；启动器以白名单构造子环境，清除继承的模型密钥、生产 JARVIS_* 配置和 NODE_OPTIONS 等。终端 Claude Code 的既有通道配置与平台开发数据分别管理。开发平台首次使用时需要按页面完成自己的初始化。

正式平台仍运行在 /opt/jarvis/current，正式 API 3140 和观测服务 3141 保持各自用途。开发使用本说明中的独立目录与入口。

本机原 apps、scripts、node_modules 和其余整个树均完整保留在 .migration-original/local，本机原目录及私密封存包也保留。Windows 原依赖、.runtime-venv 和历史工作副本作为资料留存；活动开发使用新安装的 Linux Node 依赖。本轮没有迁移或关闭联想已有开发执行器。

根部 .deployment/retired-data.json 是受保护的 Linux 控制文件，阻止误用活动项目默认 .jarvis 数据目录；原 Windows marker 留在原件中。使用本文 npm run dev 入口时，数据固定在独立 home 目录。首次进入开发页面需要自己初始化账号，生产账号和平台内模型配置未导入开发数据。

历史维护脚本、SSH 配置可能仍含 Windows 路径，不能据此认定在 112 自动可用；本轮不迁移项目目录之外的 SSH 私钥。需要运行某项维护操作时，先核对其目标机器、路径、权限和用途。

语音、OCR、ASR 及相应 Linux Python 环境尚未专项验收，不能从前端和 API 健康通过推断这些功能已经可用。完整产品功能、生产发布和人工验收仍分别确认。

Git 与项目规则

普通 npm run dev、类型检查和构建不要求项目具有 .git。初次迁移来自发布包，当时的目录没有 Git 历史，迁移本身也不代表已经初始化 Git 或提交。其后，2026-10-18 14:26:12.906068Z（北京时间22:26:12.906068）R54同步已在上述常规目录导入真实Git对象与index，main为 f8ac8a5648c16e4164dff6ced2d30f96024299b6，3158个跟踪文件逐项核同且跟踪工作树干净；这不是仅执行 git init。773项更新、26件旧版本私备份，原337条账本完整前缀保留；原件、私有运行路径、依赖和未知未跟踪文件未删除。开发入口仅完成安全配置和43140/45173端口检查，未启动开发服务或操作正式服务。见实际同步回执。本段是新的Git与源码状态切面，上文R49-r1导出说明仍保留初次迁移出处；后续实际任务须重新核对当前HEAD和dirty。

对仍无Git的历史发布包副本，不能把目录中的来源提交号当作已有对象；如需建立基线，应先确认原件、私密目录和运行数据已被忽略，只显式选择已核对的公开源码与所需文档，检查暂存区后再提交，不要直接 git add .。新的本地首次提交具有自己的提交号，不能冒认为上游提交。当前常规目录已有真实历史，不应为“补历史”重新造首次提交或用reset/clean/checkout覆盖活动文件。远端仓库、推送和外部凭据按后续明确授权处理。

部分工厂验收脚本要求被验项目存在真实 .git；scripts/package-capture-release.mjs 还会读取选定提交和 Git 对象并核对跟踪文件。仅初始化一个空仓库不会补齐这些前置条件。运行该类维护或发布脚本前，先核对它的目标项目、提交对象、输入范围与权限。

活动目录根部需同时保留 CLAUDE.md 和 AGENTS.md，并确保 AGENTS.md 引用的当前建设档案、建设日志可读。原件树里的同名历史文件用于留存，后续开发按活动根部的现行规则执行。
