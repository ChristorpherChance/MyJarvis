## 3. 用什么方法走到终点

| 失败修复 | 定位问题，形成实质修改，再复测 | 新版本或新依据产生 |
| 质量验收 | 当前人工模式核对；成熟自动模式按固定规则、独立审阅和真实证据判定 | 明确决定和采用的策略版本，正常自动路径无逐关点击 |
| 继续安排 | 依据新结果确定下一任务，必要时调整计划 | 依赖已满足，仍在授权边界内 |

一个执行进程正常结束，只说明执行完成。任务进入独立验证，再按适用人工/自动质量策略形成决定；模型的完成声明不直接变成交付。自动模式也不允许模拟、空分母、未验证或错版本放行。

首轮采用有限任务和明确出口；方法稳定之后，才逐步扩大持续监督的范围。

## 4. 贾维斯如何管理这次交付

贾维斯承担外层项目管理：维护目标、组织任务、跟踪执行、发现阻塞、汇总证据和费用、提出下一步建议。软件工厂自身承担产品内流水线，不能用自身的模拟台账给自己签发完成证明。

| 角色 | 主要职责 |
| --- | --- |
| 管理者 | 配置目标、范围、额度及模式，处理规则不能决定的异常，可随时调整或停止 |
| 贾维斯 | 保持目标与证据一致，组织下一步，提醒阻塞与风险 |
| 101 执行器 | 在任务边界内完成实际开发，提交代码及回执 |
| 验证器/独立评审 | 核查当前版本、测试与产物，保留失败证据 |
| 软件工厂 | 提供内部资料到交付的真实产品能力 |

### 4.1 建议的动态管理视图

建议逐步把项目页汇总为下面几项。现有项目、任务和用量入口可承担已有内容；尚无自动能力的部分先用明确台账记录，不宣称已自动实现。

| 管理视图 | 管理者应一眼看懂什么 | 推荐动作 |
| --- | --- | --- |
| 目标与范围 | 本轮交付内容、分期内容、最后变更原因 | 确认或调整范围 |
| 阶段路线 | 当前阶段、出口证据、下一步依赖 | 打开相关任务 |
| 当前任务 | 机器、执行器、状态、产物和验收要求 | 暂停、调整边界、验收 |
| 质量与风险 | 必测未跑、失败、模拟残留、P0/P1 缺陷 | 修复、补测试、决策 |
| 预算与恢复 | 实际 Token、估算/未知费用、剩余额度、恢复次数 | 配置预算、处理额度或凭据 |

建议的管理循环为：

**查看事实 → 找到阻塞 → 形成可执行建议 → 明确安排 → 执行与独立验证 → 更新事实。**

新增建议应带依据、收益、影响范围、所需资源及推荐优先级；未采纳的建议保持“待定”。模型提出新想法，不自动扩大开发范围或批准新预算。

### 5.1 FM-00：交付基线与真实性审计

**目标：** 把现有 PRD、历史签收、当前源码和实际证据对齐，明确哪些真实、哪些模拟、哪些尚未验证。

主要产物：

- 当前源码、依赖锁及测试环境身份。
- 需求—设计—源码—测试—证据矩阵。
- 模拟能力、历史声明差异和缺口清单。
- 完整测试命令、隔离环境方案及第一轮任务拆分。

验收出口：当前范围每条 REQ/BR 都有状态和来源；已通过项有当前证据；未知不填绿；15 项基础测试的范围准确；高优先模拟放行风险有可复现的隔离测试设计。

依赖是公开产品文档、当前源码和已保留测试证据。若资料互相矛盾，先登记差异与建议裁决，不让执行器自行改产品目标。

### 5.2 FM-01：证据真实性与放行门禁

**目标：** 让模拟、未知、未执行及过期证据无法支持正式放行。

优先验证并修复：

- 模拟标记从执行、复制回归到报告的全链路保留。
- 正常及条件放行都检查证据真实性。
- 固定覆盖率、直接通过等桩只留在显式模拟路径。
- 证据绑定当前源码、输入、运行及批次身份。

验收出口：

1. 模拟通过、模拟标记丢失、零用例、必测未跑、旧报告、输入变化、晚到回调、伪造 CI 和重复回执的反例均不能产生正式放行。
2. 拒绝过程保留原因；业务和审计事务失败不写成功决定。
3. 显式演示可以继续使用，但界面、报告及导出清楚标明模拟。
4. 真实通过、当前有效基线、无阻断缺陷的正例可以按既定策略走通：当前人工模式保留确认；成熟自动模式由质量策略决定，不要求额外逐关人工点击。

依赖独立测试数据库和可重复的测试夹具。保护现有业务数据及旧报告，不通过改旧证据“清绿”。

### 5.3 FM-02：真实单条纵向闭环

**目标：** 先让一个范围很小的实际任务完整走完编码、单测、CI、独立评审、合并和构建。

按现有 REQ-407/615，在软件工厂内部使用 Pi SDK 的沙箱 AgentSession 与工具；贾维斯外层已验证的 Claude 执行器负责完善工厂源码。两个执行边界分别记录，不能混算。

验收出口：一个明确任务产生真实代码差异及提交、实际单测/CI 退出码与测试数量、独立评审结论、实际仓库构建工件及指纹。暂停、停止、接管、预算、运行身份及失败恢复有效；返回“完成”但没有产物时不能通过。

依赖可执行的沙箱镜像、按用途模型配置、限定工作区、Git/CI 适配和可信回传。已有 LocalCiAdapter 的本地标识和未知状态不能冒充实际 CI。

若使用不具备工具或沙箱能力的目标，记录阻塞并更换已核实的执行路径；不能悄悄降级成模拟通过。

### 5.4 FM-03：当前版本全量隔离验证

**目标：** 从基础检查扩大到当前源码的完整适用测试，形成可复验的质量结论。

使用独立 PostgreSQL、Redis、MinIO 及测试数据，先验证环境隔离，再运行完整单元/集成测试、命令门禁、浏览器关键旅程、安全与恢复检查。测试目录、命令和结果必须对应当前冻结版本。

验收出口：

- lint、类型检查、依赖方向、错误码闭集、构建及适用测试通过；必测不允许跳过冒充通过。
- 覆盖率按现有工程纪律核对：普通包行 ≥80%/分支 ≥70%；证据、策略、命令事务相关包 ≥90%/80%，数据来自真实报告。
- 原型/实现关键行为与当前页面一致；实际浏览器证据能指向测试对象。
- 迁移、失败回滚、审计链、备份恢复在独立环境验证。
- P0/P1 缺陷完成修复与独立回归；允许分期或遗留的内容单列理由及影响。

历史 151 项测试和旧覆盖率仅是参考，复跑前不能记作当前通过。规模压测、部署安全差异等按现有 PRD 优先级和约定范围逐项处理。

### 5.5 FM-04：真实示范项目贯通

**目标：** 证明整个产品能够把资料转成一个可运行的软件项目，并完成真实验收与交付决定。

推荐一个最小示范：**本地待办清单**。范围候选为新增、编辑、完成、删除、状态筛选及本地持久化；不引入登录、支付或外部业务接口。这是建议，示范项目名称、功能和验收样例仍待确定。

它应同时包含成功路径、无效输入和至少一次实际失败修复，不只演示顺利点击。

验收出口：

- 原件、解析稿、经质量检查的定稿以及需求版本真实存在；辅助模式人工确认，成熟模式自动检查与定稿。
- 原 PRD 的 RTM 指标保留为历史口径：L0a ≥95%、L0b=100%，开发前 L0c=100%；R21 另要求本期全部必需条款 100% 承接和真实验证，不用空范围或旧比例代替新增目标。
- 设计和原型与任务有追踪，代码及候选构建真实运行。
- UI 按每页、每适用视口判定：关键项 100%、一般项 ≥95%、严重偏差 0；不跨页平均掩盖不达标。
- 至少一次“失败 → 实质修复 → 新构建/批次 → 独立回归”，按当前人工或成熟自动复验关单规则关闭缺陷。
- 七个质量门及不可变批次/报告/决定都有身份和审计；当前人工模式和成熟自动模式分别验证。
- 从干净环境能够按说明启动交付工件，指纹可复核。

这一阶段先验证小场景，再扩展到全部约定功能和格式；示范成功不能代替所有需求的完整验收。

### 5.6 FM-05：交付与可持续维护

**目标：** 交付一套能安装、使用、升级、恢复和继续完善的软件工厂。

验收出口：范围内验收证据齐全，P0/P1 解决，遗留项明确；真实工件及操作说明可复现；备份恢复与回滚有实际验证；按适用质量策略核对最终报告并记录交付决定。当前辅助模式由人确认，成熟全自动模式由真实证据决定，无额外逐关点击。

源码、文档、依赖锁、构建、环境与证据应形成一致的版本组合。后续变更保留旧记录，并把受影响的结论标为待复核。

此阶段需要实际生成并验证交付文件。贾维斯的“交付包”记录目前是台账：记录名称和证据链接，不会自动打包源码、生成安装文件或证明文件可运行。

## 6. 推荐首个正式任务

### 6.1 FM-001：软件工厂交付基线与真实性审计

建议先安排一个只读审计任务，避免直接把“完善整个软件工厂”交给执行器无限循环。

**目标：** 根据冻结 PRD 和当前公开源码，建立真实能力、模拟边界、测试及交付证据矩阵；识别阻断最终目标的差异，形成第一轮可独立验收的任务及隔离反例测试设计。

**验收标准：**

1. 当前范围全部 REQ/BR 有状态、源码位置、测试及证据来源；缺失项明确为未知或待补。
2. 已有构建、类型检查和 15 项基础测试如实引用当前回执，不扩写成全量验收。
3. 开发/质量/构建/自测/自动用例的模拟边界列全。
4. 模拟标记与正常放行风险有独立环境复现方案；未实际复现时保持“待验证”。
5. 给出按依赖排序的补齐任务，每项有写范围、产物、验收、预算需求及停止条件。
6. 不修改源码、运行配置、业务数据库及历史证据，不触发模型功能测试或工厂放行。

**输入：** PRD/RTM/LLD、当前公开源码身份、已有回执、历史验收文件、服务器和执行器状态。私有环境及凭据只以受控配置引用，不上传到文档或执行日志。

## 7. 与已有平台里程碑如何对应

平台已有三个里程碑保持原名和历史记录，细路线映射到它们，不重建里程碑或伪造已完成比例。

| 现有里程碑 | 对应推荐细阶段 | 当前证据 |
| --- | --- | --- |
| 确认代码与真实测试基线 | FM-00；为 FM-01 准备反例与隔离环境 | 新基线、现有 306 项测试及门禁反例已有首轮证据；新需求完整矩阵尚待形成 |
| 完成真实执行及测试能力 | FM-01、FM-02、FM-03 | 通信已验证；内部真实编码/构建/用例流水线仍待完善和验收 |
| 完成独立验收与交付 | FM-04、FM-05 | 尚未完成真实示范和最终交付验收 |

当前任务接口一个任务只有一个 `dependsOn`。推荐先串成清楚的主线：

**基线审计 → 真实性门禁 → 单条真实闭环 → 全量隔离验证 → 真实示范 → 交付验收。**

有多项依赖时，把主依赖写入 `dependsOn`，其他前提写进任务验收/输入清单，在启动前核对；不能用一个字段宣称已实现任意依赖图调度。以后需要并行、多依赖和自动门禁时，再单独设计扩展。

代码修改任务按一个写者、独立工作区和明确写范围安排；可并行的文档/测试准备必须避免覆盖同一工件。

| 情况 | 推荐处理 | 可以继续的证据 |
| --- | --- | --- |
| 完成声明无产物 | 进入待核验，要求实际差异/报告 | 产物存在且身份匹配 |
| 同一错误反复出现 | 停止无变化重跑，定位原因和修复计划 | 实质代码/环境或输入变化 |
| 模型额度不足 | 标记额度阻塞，保留检查点，按已知重置时间等待 | 额度恢复或已核实后备可用 |
| 后备模型可切换 | 只使用已配置、可连接、任务兼容且预算允许的目标 | 切换记录、检查点和计量归属 |
| 网络暂时异常 | 有限退避重试，到上限停止 | 网关恢复且同一请求不重复提交 |
| 登录/权限问题 | 交给管理者处理凭据或权限 | 认证/权限验证成功 |
| 进程无新产物 | 对比心跳、日志及输出变化，执行超时边界 | 有新证据或明确阻塞 |
| 服务异常 | 先诊断影响范围，遵循现有远控审批和操作记录 | 有诊断依据与明确操作范围 |
| 目标变更 | 暂停活动执行，更新边界，旧验收失效 | 新目标版本与重新确认的依赖 |

不要因模型额度耗尽、网络错误或日志停顿盲目重启整台服务器；重启可能打断其他项目和后台任务。恢复应针对已诊断的原因，重启是单独的运维动作。

贾维斯只在任务目标、预算、轮次、时限和权限内续做；达到出口进入独立验收，按当前辅助或成熟自动策略继续。阻塞无法自行解决时给出“原因、已尝试什么、推荐选项、影响”，而不是无限问模型下一步。

有限恢复策略能处理部分额度和瞬时网络故障，不能保证所有异常无人值守解决，也不能保证外部供应商硬额度被本地预算完全控制。

## 9. 如何衡量真正的进度

先建立分母，再展示进度。分母是冻结范围内的验收条款，不是执行器生成的任务数；批准分期单列，不能悄悄删除。

| 指标 | 计算或展示方法 |
| --- | --- |
| 范围覆盖 | 已有清楚承接关系的条款 / 当前范围条款 |
| 真实实现 | 已有当前真实实现与核验证据的条款；模拟单列 |
| 验收进度 | 已独立验证并验收通过的必需条款 / 当前必需条款 |
| 质量 | 失败、必测未跑、过期证据、P0/P1 缺陷及回归状态 |
| 阶段准备 | 每个出口条件逐项完成/失败/未知 |
| 资源 | 实际 Token、可靠计价、目录估算、未知费用及恢复次数 |
| 交付准备 | 实际工件、安装使用、恢复、手册和适用质量策略的决定是否齐全 |

目前缺少完整的当前需求—证据矩阵，因此不发布软件工厂源码完成百分比。模型时长、Token 消耗、对话次数和内部看板进度可描述工作活动，不能作为产品完成率。

新增或修改范围后保留原分母、变更原因和新版本，避免看起来“进度倒退”却不知道为什么。源码或输入身份变化后，受影响证据标为待复核；旧测试结果不自动套到新提交。
